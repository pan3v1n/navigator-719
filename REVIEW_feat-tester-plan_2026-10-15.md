# Ревью `feat/tester-plan` (`git diff 55e8910..08de28d`) — 15.10.2026

Коммиты: `7c9c4ab` (демо-чат лендинга), `50af8a1` (цены + вкладка «Тестирование» + `/admin/testers`),
`08de28d` (#191). Решения владельца из постановки (цены, ×12, «от 240 000 ₽/год», «1 ₽ первая неделя»,
бесплатный безлимитный «Тестировщик» после подтверждения admin'ом, ПДн только в «Заявках») — требования,
находками не считаются. HIGH-находок нет.

## Находки

1. **MED — «Снять тариф» у тестировщика даёт ему бессрочный безлимит.**
   `app/api/admin.py:734` (`admin_tester_revoke` → `q.set_user_plan(db, user_id, None)`).
   Дефект: без тарифа у учётки нет ни лимита (`plans.plan_limit` → `ALL_PLANS.get("")` = None,
   `app/core/plans.py:43`), ни срока (`plan_expired` при пустом `plan` → False, `plans.py:53`), то есть
   снятие «Тестировщика» не закрывает доступ, а снимает и лимит, и срок.
   Сценарий: тестировщик с доступом «до 20.10.2026»; admin в разделе «Тестировщики» жмёт «Снять тариф»
   (подтверждение: «Снять тариф «Тестировщик» у …?», флеш «Тариф «Тестировщик» снят») → учётка получает
   «Без тарифа — без ограничения числа запросов» (так пишет и `admin/user.html`) навсегда. Если бы admin
   ничего не делал, 20.10 доступ закрылся бы (402). Отзыв даёт больше доступа, чем бездействие.
   Исправление: в отзыве закрывать доступ явно. Варианты: оставить план и поставить срок
   «истёк сегодня» (`expires_at = plans.anchor_from_date(plans.msk_today())`), или блокировать учётку,
   или назначить «Пробный режим» с истёкшим сроком. Минимум — поменять текст кнопки/подтверждения так,
   чтобы admin видел: учётка остаётся без лимита. Тест: после revoke `plan_limit`/`plan_expired`
   должны закрывать вопросы (сейчас `tests/test_testers.py` проверяет только, что `plan is None`).

2. **LOW — повторное «Подтвердить» затирает срок и дату подключения действующего тестировщика; статус
   заявки не проверяется.** `app/api/admin.py:690-711` (`admin_tester_approve`).
   Дефект: маршрут не проверяет ни `lead.status` (новая/в работе), ни то, что учётка уже тестировщик.
   Сценарий 1: заявка в очереди с бейджем «уже тестировщик» (учётке тариф уже дали в карточке со сроком
   «до 31.10»), admin жмёт «Подтвердить» с пустым «До» → `plan_started_at` = сегодня, срок = бессрочно.
   Сценарий 2: две вкладки админки; в одной заявку отклонили, во второй (устаревшей) жмут «Подтвердить» →
   отклонённая заявка становится «Подключена», учётка получает безлимит.
   Исправление: 409/422, если `lead.status not in ("new", "in_work")`; для учётки, уже имеющей
   «Тестировщика», не трогать `started_at`/`expires_at` (или требовать явного срока), а заявку
   просто закрывать как «Подключена».

3. **LOW — поле «До» в очереди разрешает сегодняшнюю дату, сервер её отвергает голым JSON.**
   `app/web/templates/admin/testers.html:33` (`min="{{ today }}"`) против `app/api/admin.py:699`
   (`until <= today` → 422).
   Сценарий: admin выбирает в календаре сегодняшнее число (браузер разрешает, `min` = сегодня) → вместо
   страницы — `{"detail":"Срок действия должен быть позже сегодняшнего дня"}`.
   Исправление: `min` = завтра (`(plans.msk_today() + timedelta(days=1)).isoformat()`), либо принимать
   «сегодня» как «последний день — сегодня» по той же логике, что `anchor_from_date` в карточке.

4. **LOW — корпоративная цена на сервере считается, но нигде не показывается.**
   `app/api/web.py:391-397` + `app/web/templates/profile.html:134-160`.
   Дефект: `confirm.price` выводится только в панели `{% if confirm and not confirm.popup %}`, а
   корпоративный выбор и «Для организаций» всегда идут в попап (`popup = kind == "corporate" or …`),
   где цены нет. Ветка `kind == "corporate"` в `pricing.price_line` (цена × пользователи × 12) на сервере
   мёртвая; коммит же обещает «Цена — в подтверждении заявки».
   Сценарий: «Стандарт», корпоративный, год, 3 польз. → попап «Тариф «Стандарт»: корпоративный · год ·
   3 польз. …» без «536 400 ₽/год»; на карточке сумма была.
   Исправление: вывести `{{ confirm.price }} без НДС` в тексте попапа (обе ветки — для ORG_TARIFF это
   «от 240 000 ₽/год»), и добавить тест на попап.

5. **LOW — корпоративная сумма не пересчитывается при загрузке страницы.**
   `landing/app.js:146-160`, `app/web/templates/profile.html` (скрипт витрины, `reprice`).
   Дефект: `reprice()` вешается только на `change`/`input`/кнопки ±, начального вызова нет. Браузер
   восстанавливает значения полей при перезагрузке (Firefox) и при «Назад» (bfcache), а текст суммы — нет.
   Сценарий: на корпоративной карточке «Профи» выбрали «год», 5 польз., перезагрузили страницу → поля
   показывают «год» и 5, сумма — «19 900 ₽/мес»; по «Подключить» в заявку уходит год × 5.
   Исправление: вызвать `reprice()` один раз при инициализации каждой карточки (и на `pageshow`).

6. **LOW — у тестировщика с истёкшим сроком кнопка на вкладке «Тестирование» заблокирована.**
   `app/web/templates/profile.html:189` (вкладка tester: `{% if user.plan == pricing.TESTER_TARIFF %}…disabled>Подключён`).
   Сценарий: срок теста кончился (`plan_expired` → вопросы 402), в кабинете на вкладке написано
   «Подключён», кнопки нет — повторную заявку из кабинета не подать.
   Исправление: условие `user.plan == TESTER_TARIFF and not plan.expired` (или `plans.plan_expired(user)`),
   иначе показывать «Подать заявку» / «Продлить тест».

7. **LOW — очередь «Тестировщики» усечена с головы, счётчик врёт.**
   `app/db/queries.py:537` + `app/api/admin.py:670`.
   Дефект: `list_tester_leads(limit=LEADS_ON_PAGE)` сортирует старые сверху и режет хвост, а шапка
   «заявок ждут решения: N» считает `requests|length` — то есть показывает не больше лимита, а новейшие
   заявки при переполнении не видны вовсе. Аналогично ссылки «Создать учётку» ведут на
   `/admin/leads#lead-N`, а раздел «Заявки» тоже усечён `LEADS_ON_PAGE` — у старой заявки якоря нет.
   Исправление: отдельный `count` для шапки и пометка «показаны первые N»; для ссылки — фильтр
   по статусу или страница заявки.

## Что проверено и оказалось верным

- `pricing.parse_options` / `lead_kind` / `price_line` для всех сочетаний тариф × вид (individual /
  corporate / tester) × проба: «Тестировщик» с вкладки «Тестирование» и чипом лендинга (вид не шлётся →
  `individual` → `lead_kind` по тарифу = `tester`) сохраняется как `tester`; `kind=tester` у не-тестировщика
  и `corporate` у тестировщика отвергаются; проба — только «Старт»/individual. `create_lead` теперь
  сохраняет `tester`. `_renewal` даёт цену только личным платным тарифам, корпоративное продление — попап.
- Новые POST-маршруты защищены `Depends(require_admin)`, как существующие; GET `/admin/testers` — `_gate`.
  Все ORM-объекты читаются внутри сессии (`_tester_verified` в `_card` — до `expunge`). ПДн заявок
  (имя/почта/телефон) раздел не выводит — только номер, дата, организация, учётка.
- `set_user_plan`: подтверждение пишется при первом назначении «Тестировщика», не перезаписывается при
  пересохранении, снимается при смене тарифа; миграция — два `ADD COLUMN` в `_ensure_columns`.
- Лендинг: три вкладки переключает `#pricing [data-panel]` (включая сноски), пересчёт только у
  `.plan[data-price]` (корпоративные), формат «536 400» совпадает с `pricing.rub`; демо-сайзер — копии
  в той же ячейке сетки, `visibility:hidden`, id не дублируются.
- #191: «сейчас» = полдень МСК текущих суток; все окна `summary_view` ограничены только снизу
  (`since`), поэтому реплики «в будущем» относительно настенных часов (запуск в 00:30) и записи с
  реальным `now` (гостевая реплика, лиды) попадают в те же сутки при любом времени запуска; подмена
  `summary_view` в `test_page` передаёт тот же момент. Тест остаётся содержательным.
