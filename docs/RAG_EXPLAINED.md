# Как устроен RAG в Навигаторе ПП №719 — простыми и сложными словами

> Пояснительная записка по архитектуре поиска и генерации ответа. Простой уровень —
> «как другу», сложный — по коду с файлами, строками и формулами. Связанные документы:
> [V1_SPEC.md](V1_SPEC.md) (полная спецификация), [IDEAS.md](IDEAS.md) (бэклог),
> [BUDGET.md](BUDGET.md) (стоимость). Файлы кода: `app/rag/*`, `app/core/prompts.py`.

---

## Сначала: какие «модели» вообще есть в сервисе

Их **три**, и они разные по природе — это ключ к пониманию:

| # | Что | Где живёт | Платная? | Роль |
|---|---|---|---|---|
| 1 | **e5-large** (multilingual-e5-large) | локально, в RAM, на CPU | нет | превращает текст в **смысловой вектор** (1024 числа) |
| 2 | **BM25** (`app/rag/sparse.py`) | локально, **это не модель, а формула** | нет | превращает текст в **вектор по словам** (какие термы и как часто) |
| 3 | **DeepSeek** `deepseek-chat` | удалённо, по API | да (копейки) | **пишет финальный ответ** по найденному контексту |

Плюс **Qdrant** — это не модель, а векторная БД: хранит всё и **ищет + сливает** два поиска воедино.

Запомни деление: **1 и 2 — ищут** (retrieval), **3 — генерирует** (generation). Это и есть «RAG»
= Retrieval-Augmented Generation: сначала находим, потом генерируем по найденному.

---

## Простой вариант (суть в 5 шагов)

```
   Пользователь: "производим прицепы для легковых авто"
            │
            ▼
   ┌─────────────────────────────────────────────┐
   │ 1. Запрос превращаем в ДВА вектора:          │
   │    • e5  → "о чём это по смыслу"  (модель)    │
   │    • BM25 → "какие слова"          (формула)  │
   └─────────────────────────────────────────────┘
            │
            ▼
   ┌─────────────────────────────────────────────┐
   │ 2. Qdrant ищет похожее ДВУМЯ способами        │
   │    и сливает результаты (RRF).                │
   │    (+ если есть код ОКПД2 — поднимает его)    │
   └─────────────────────────────────────────────┘
            │
            ▼
   ┌─────────────────────────────────────────────┐
   │ 3. Берём топ-5 позиций 719 из базы            │
   │    (раздел, баллы, операции) = КОНТЕКСТ        │
   └─────────────────────────────────────────────┘
            │
            ▼
   ┌─────────────────────────────────────────────┐
   │ 4. Контекст + вопрос → DeepSeek (LLM)         │
   │    "ответь СТРОГО по этому тексту"            │
   └─────────────────────────────────────────────┘
            │
            ▼
   ┌─────────────────────────────────────────────┐
   │ 5. Готовый ответ + пометка "решает эксперт"  │
   └─────────────────────────────────────────────┘
```

Идея одна: **LLM не знает 719 наизусть и не должна выдумывать**. Мы сами находим нужный кусок
регламента в базе и подсовываем его модели — она лишь красиво и по делу пересказывает найденное.
Поэтому она не врёт про баллы.

## Сложный вариант (по коду, с двумя фазами)

RAG живёт в **двух фазах**: одна разовая (наполнение базы), вторая — на каждый запрос.

### ФАЗА A — Индексация (офлайн, разово) — `scripts/load_kb.py`

Происходит один раз (~17–25 мин на CPU), результат лежит в Qdrant постоянно.

```
knowledge_base/pp719/structured/*.json   (1672 продукта, 29 разделов + методички)
        │
        │  для каждого продукта берём текст (наименование + операции)
        ▼
   ┌──────────────────────┐        ┌──────────────────────────────┐
   │ e5-large.encode()    │        │ sparse.document_vector()     │
   │ "passage: <текст>"   │        │ BM25 TF с нормировкой длины  │
   │ → dense [1024 float] │        │ → (indices[], values[])      │
   │  (модель, ~2ГБ RAM)  │        │  (формула, без модели)       │
   └──────────┬───────────┘        └───────────────┬──────────────┘
              │                                     │
              └──────────────┬──────────────────────┘
                             ▼
              ┌──────────────────────────────────────┐
              │ Qdrant: 1 точка = 1 продукт          │
              │   • dense-вектор   (named "dense")    │
              │   • sparse-вектор  (named "bm25")     │
              │   • payload = ВСЯ структура продукта  │
              │     (раздел, ОКПД2, порог, операции)  │
              │   • индексы по okpd2_codes/section    │
              └──────────────────────────────────────┘
```

Важные детали:
- **e5 нужны префиксы**: документы — `passage: …`, запросы — `query: …`
  (`app/rag/embeddings.py:34,40`). Это требование модели e5.
- **BM25 без скачивания модели** (`app/rag/sparse.py`): токенизация → Snowball-стемминг
  (`py_rust_stemmers`) → хэш терма в число (`mmh3`). IDF потом считает **сам Qdrant**
  (`Modifier.IDF`). Формула документа с нормировкой по длине (`sparse.py:55-67`):
  ```
  value = tf·(k1+1) / (tf + k1·(1 − b + b·dl/avgdl))     k1=1.2, b=0.75
  ```
  Нормировка по длине (`dl/avgdl`) — критична: без неё мега-записи (методичка X на 393 строки)
  забивали бы топ на любой запрос.
- **Кэш эмбеддингов** `.emb_cache/`: повторная индексация считает только изменённые чанки
  (0.02с из кэша vs 2.5с).

### ФАЗА B — Запрос (онлайн, на каждый вопрос) — `pipeline.answer()`

```
              Вопрос пользователя (+ опц. код ОКПД2)
                          │
        ┌─────────────────┴──────────────────┐
        ▼                                     ▼
  retriever.search()                   retriever.search_cases()
  (основная база pp719)                (коллекция verified_cases)
        │                                     │
        ▼  _hybrid()  retriever.py:89         │  тот же гибрид по кейсам
  ┌───────────────────────────────────────┐  │
  │ embed_query(q)   → dense  (e5, модель) │  │
  │ sparse.query_vector(q) → bm25 (формула)│  │
  │            ▼                            │  │
  │ Qdrant.query_points(                   │  │
  │   prefetch=[ dense top-20,             │  │
  │             bm25  top-20 ],            │  │
  │   query=FusionQuery(RRF) )             │  │  ← RRF сливает 2 списка
  └───────────────┬───────────────────────┘  │     в один ранг
                  ▼                            │
        ОКПД2-буст/подстраховка                │
        (retriever.py:119-141)                 │
        совпал код → наверх,                   │
        нет в пуле → отдельный                 │
        жёсткий запрос по префиксам            │
                  │                            │
                  ▼                            ▼
              top-5 Hit                   top-3 кейса
                  │                            │
                  └──────────────┬─────────────┘
                                 ▼
             format_context() + format_cases()  (pipeline.py:32,58)
             усечение операций до 12/хит (MAX_OPS_PER_HIT)
                                 │
                                 ▼
        ┌──────────────────────────────────────────────┐
        │ DeepSeek chat.completions (pipeline.py:98)    │
        │  system = NAVIGATOR_SYSTEM_PROMPT             │
        │  user   = вопрос + КЕЙСЫ + НАЙДЕННЫЕ ПОЗИЦИИ  │
        │  temperature = 0.1  (минимум фантазии)        │
        └───────────────────┬──────────────────────────┘
                            ▼
        _ensure_disclaimer()  → гарантирует пометку эксперта
                            ▼
                   Ответ (text + hits + cases)
```

Что тут принципиально:

1. **Гибрид = два поиска + RRF.** Dense (e5) ловит **смысл** («чиллеры» →
   «компрессорно-конденсаторные блоки», слова разные). BM25 ловит **точные слова/коды/термины**.
   RRF (`Fusion.RRF`) сливает оба ранга — берёт лучшее от каждого. Это `retriever.py:96-105`.

2. **ОКПД2-буст** (`retriever.py:119-141`) — если пользователь дал код, позиции с совпадающим по
   иерархии кодом поднимаются наверх; если их вообще нет в пуле — делается отдельный жёсткий
   фильтрованный запрос по префиксам кода (подстраховка `MatchAny`). Код — сильный сигнал
   поверх семантики.

3. **Петля кейсов** (`search_cases` + правило 1а промпта) — подтверждённые экспертом ответы идут
   в контекст с **высшим приоритетом**. Сейчас коллекция пустая (ждёт эксперта), но механизм готов:
   graceful при пустой коллекции (`retriever.py:153-157`).

4. **Защита от галлюцинаций — на трёх уровнях:**
   - `temperature=0.1` (модель почти не «творит»);
   - системный промпт (`prompts.py:114-133`): «опирайся ТОЛЬКО на контекст, баллы дословно,
     нет позиции — честно скажи»;
   - `_ensure_disclaimer` (`pipeline.py:78`) — пометка эксперта дописывается принудительно,
     даже если LLM её забыла.

5. **«Не найдено»** (`pipeline.py:85`) срабатывает только если **и** позиции, **и** кейсы пусты.
   ⚠️ Здесь зарыта дыра из IDEAS: Qdrant на непустой коллекции **всегда** что-то вернёт, поэтому
   запрос вне 719 («хлеб») даёт «ближайший мусор», а не честное «вне сферы». Это и есть
   **out-of-scope guard** (нужен порог по dense-сходству) — см. `docs/IDEAS.md`, раздел RAG.

## Где какая модель — сводка одной картинкой

```
┌──────────────── ЛОКАЛЬНО на сервере (RAM/CPU) ────────────────┐
│                                                                │
│   e5-large ──► смысловой вектор   (зачем нужна RAM 4–8 ГБ)      │
│   BM25     ──► словарный вектор   (почти ничего не ест)         │
│   Qdrant   ──► хранит + ищет + RRF + IDF  (данные крошечные)    │
│                                                                │
└────────────────────────────┬───────────────────────────────────┘
                             │ только финальная генерация уходит наружу
                             ▼
┌──────────────── УДАЛЁННО по API (платно) ─────────────────────┐
│   DeepSeek deepseek-chat ──► пишет ответ по контексту           │
│   (~₽0.11 за запрос; данные контекста уходят в DeepSeek)        │
└────────────────────────────────────────────────────────────────┘
```

Это связывает частые вопросы по эксплуатации:
- **RAM-зависимость** — из-за e5 (блок «локально»). BM25 и Qdrant почти бесплатны по памяти.
- **«Прогрев» модели** — это первая загрузка e5 в RAM при старте процесса (кэш `lru_cache` на
  процесс; перезапуск UI → прогрев заново).
- **«Вынести модель в API»** — означало бы убрать e5 из левого блока, но тогда нужен
  РФ-эмбеддинг-API (Yandex/GigaChat), иначе ломается принцип RF-first (см. `CLAUDE.md`, принцип №3).
- **Платный только DeepSeek** (правый блок); весь поиск — слева, локальный и бесплатный.

## Минимальные требования к серверу (следствие архитектуры)

Связывающий ресурс — **RAM** (из-за e5). Подробнее — `docs/BUDGET.md`.

| Параметр | Минимум (впритык) | Рекомендуется | Почему |
|---|---|---|---|
| RAM | 4 ГБ | 8 ГБ | e5-large резидентно ~3–4 ГБ; 4 ГБ рискует OOM при энкодинге |
| vCPU | 2 | 4 | GPU не нужен; на запрос — 1 короткий энкод; больше ядер ускоряют индексацию |
| Диск | 20 ГБ | 30–40 ГБ | OS + torch CPU (~3–5) + модель (~2.1) + Qdrant (<0.1) + кэши |

Снизить RAM можно только сменой эмбеддера: `e5-base` (влезает в 4 ГБ, чуть хуже ретрив),
`e5-small`, или BM25-only (без dense, ~1–2 ГБ, но заметно хуже на «своих словах» — теряется
семантика).
