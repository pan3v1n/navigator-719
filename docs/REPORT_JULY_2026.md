## 0. Резюме для заказчика

За июль сервис прошёл путь от инженерного прототипа до работающего многопользовательского
веб-приложения, развёрнутого в облаке и **протестированного 17 региональными торгово-промышленными
палатами** в двух волнах.

**Главные факты периода:**

| Что | Значение |
|---|---|
| Развёрнутых релизов на боевой сервер | **4** (02.07, 06.07, 15.07, 21.07) |
| Коммитов в кодовую базу | **57** |
| Автотестов (все зелёные) | **42 → 105** |
| Пользователей в системе | **28** (17 регионов) |
| Вопросов, обработанных сервисом | **604** (1208 реплик диалога, 163 сессии) |
| Оценок ответов от экспертов | **247**, из них со звёздами **147** |
| Текстовых отзывов и исправлений | **150** (124 комментария + 26 экспертных исправлений) |
| **Приёмочная метрика (доля ответов ≥4★)** | **33 %** при целевом гейте **≥70 %** — **не пройден** |
| Стоимость эксплуатации (LLM) за весь период | **≈ 140 ₽** |

**Как это читать.** Приёмочный гейт не пройден — это честный результат, и он был получен ровно так,
как задумывалось: тест проводился на широкой независимой аудитории, без «подготовленных» вопросов.
При этом анализ 150 текстовых отзывов показал, что **низкие оценки сконцентрированы в шести
конкретных, воспроизводимых и устранимых причинах** (а не в общем «модель плохо отвечает»):
недостающие фрагменты нормативного корпуса, не проиндексированные Примечания с порогами баллов,
методика работы с кодами ОКПД2 и удержание контекста в диалоге. Одна треть всего негатива дана
одним въедливым тестировщиком (Томская область, 74 из 150 отзывов) — это **ценный
концентрированный сигнал**, а не шум.

К концу июля **бо́льшая часть выявленных причин уже устранена в коде и развёрнута** (см. §7): в
корпус добавлены тело Постановления №719 и Приказ ТПП РФ №52, заработали пороги из Примечаний,
поиск по частичному коду ОКПД2, перевод ТН ВЭД↔ОКПД2, стриминг ответа и переработанная
админ-панель. Первые наблюдения по логам после доработок (§8) показывают движение в правильную
сторону, но объём данных пока недостаточен для вывода — **требуется повторный замер приёмки**.

**Позиция на конец июля:** сервис живой, стабильный, используется реальными экспертами;
диагностика проблем полная и трассируемая; план доработок утверждён и наполовину выполнен;
следующий обязательный шаг — контрольная волна тестирования для повторного замера приёмки.

### 2.3. Инфраструктура и эксплуатация

- **Развёртывание:** Docker Compose (приложение + векторная БД Qdrant), образ собирается на сервере,
  инструкция `docs/DEPLOY.md`. Данные — в именованных томах, переживают пересборку и рестарт.
- **Хостинг:** Yandex Cloud, Ubuntu 24.04, 2 vCPU / 8 ГБ / SSD 30 ГБ, порт 80. С 06.07 машина
  работает круглосуточно (по решению заказчика — чтобы не менялся адрес).
- **Модель веток:** `prod` (то, что развёрнуто) → `main` (стабильная) → `dev` (интеграция) →
  `exp/*` (эксперименты). Слияние `dev → main` — через pull request с код-ревью.
- **Резервные копии:** консистентные снимки БД (SQLite `.backup`, не «сырое» копирование) перед
  каждым деплоем; за июль сделано 3 предеплойных бэкапа + 3 полные выгрузки данных.
- **Безопасность:** пароли — bcrypt; обязательный секрет сессий в production (сервис не стартует
  без него); анонимный доступ к API закрыт; таймаут обращения к LLM; хэши паролей вырезаются из
  всех выгрузок.

### Два критичных класса ошибок (P0)

**(A) Продукция вне Приложения 719 → механизм СТ-1.** Система уверенно и неверно закрывала
заявителю путь: «без позиции в приложении подать заявление нельзя», «получить СТ-1 по ПП №719
невозможно», а также выдумывала несуществующий документ «заключение ТПП».
*Корень:* системный промпт держал модель строго внутри Приложения; тело Постановления №719
(где подпункт «г» пункта 1 описывает путь через СТ-1) **не было в корпусе**.
*Это самый опасный класс ошибок — заявителя разворачивают там, где путь есть.*

**(B) «Какие документы готовить» — самый частый вопрос заявителя** — уходил в обобщённый ответ о
порядке действий, потому что **Приказ ТПП РФ №52 отсутствовал в корпусе** (получен от заказчика
только 20.07 и проиндексирован 21.07).

### Корректность ядра (P1)

- **Пороги из Примечаний** («Порог: в контексте не указан») — нумерованные примечания приложения
  не структурировались и не индексировались.
- **Обязательные vs балльные** требования не разделялись; операциям без баллов приписывалась
  возможная балльная оценка.
- **Методика ОКПД2**: не отрабатывались «из», уровни подгрупп, сверка с официальным классификатором.
- **Диалог**: терялся уже подтверждённый код; предложенное системой действие («хотите, поясню?»)
  не выполнялось на «поясни».

### 26 исправлений = готовый обучающий материал

Эксперты не просто критиковали — **дали эталонные ответы** (варикапы → путь СТ-1; кабели 110–550 кВ
есть в 719; насосы — требование к закалке есть; порог 22.22 ≥90 баллов по прим. 7; дисплеи —
порог 205 баллов до 31.12.2027 и т. д.). Это прямой вход в «петлю обучения» сервиса: 5 кейсов уже

## Приложение Б. Методика расчёта метрик

- **Приёмочная метрика:** доля записей обратной связи вида «оценка ответа» со звёздами ≥4 от общего
  числа записей со звёздами. Аккаунт `admin` исключён как демонстрационный/технический. Записи без
  звезды (только текст) в метрику не входят — они дают диагностику, а не оценку.
- **Токены и стоимость:** суммы по полям `prompt_tokens` / `completion_tokens` таблицы сообщений;
  тариф DeepSeek $0.27 / $1.10 за 1 млн входных/выходных токенов, курс 90 ₽/$ (оценочно).
- **Лабораторные метрики поиска:** прогон эталонных наборов напрямую по поисковому слою, без
  обращения к LLM — детерминированно и бесплатно. Эталон — раздел или конкретная позиция.
- **Faithfulness:** доля ответов, в которых все упомянутые числа баллов/процентов присутствуют в
  переданном модели контексте; проверка автоматическая, дословным сопоставлением.
- **Признаки в ответах (§8):** подстрочный поиск характерных формулировок по текстам 604 ответов;
  метод грубый, служит индикатором динамики, а не точным измерением.
