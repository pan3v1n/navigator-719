# Тестирование Навигатора ПП №719 с экспертом Курской ТПП

Документ для приёмочного теста продукта (движок 0.5.0 / веб-чат мини-1.0). Две роли: **оператор** (запускает систему) и
**эксперт ТПП** (оценивает ответы). Цель — на 5–10 реальных кейсах проверить, помогает ли
навигатор и где ошибается, и запустить петлю обучения.

> ⚠️ **Главный принцип:** ИИ выдаёт **черновик-подсказку**, а не заключение. Окончательный
> вердикт всегда за уполномоченным экспертом ТПП. Тест проверяет полезность подсказки, а не
> заменяет экспертизу.

---

## Часть 1. Запуск системы (оператор)

Выполняется один раз перед сессией тестирования. Нужен ПК с развёрнутым проектом.

1. **Поднять Qdrant** (база векторов). Запустить Docker Desktop и дождаться, пока он
   стартует (контейнер Qdrant поднимется сам, autorestart). Проверка:
   ```
   curl http://localhost:6333/healthz      → healthz check passed
   ```
2. **Проверить `.env`** в корне проекта — должен быть задан `DEEPSEEK_API_KEY`
   (скопировать из `.env.example`, вставить ключ с platform.deepseek.com).
3. **Загрузить базу знаний в Qdrant** — только если коллекция ещё не загружена
   (данные хранятся постоянно, повторять не нужно):
   ```
   .venv\Scripts\python scripts\load_kb.py
   ```
   Ожидаемо: `Коллекция 'pp719': точек = 1357`. (~15–25 мин на CPU, разово.)
4. **Загрузить кейсы** (на старте их нет — коллекция будет пустой, это нормально):
   ```
   .venv\Scripts\python scripts\seed_cases.py
   ```
5. **Запустить интерфейс:**
   ```
   .venv\Scripts\python -m streamlit run frontend\streamlit_app.py
   ```
   Откроется браузер на `http://localhost:8501`. Передать эту ссылку эксперту
   (или показывать с того же ПК).

**Если что-то не открывается:** проверить пункты 1–2 (Qdrant поднят, ключ задан). Ошибки
в окне Streamlit подскажут причину.

## Часть 2. Как пользоваться (эксперт)

1. В поле **«Опишите продукцию или задайте вопрос»** ввести запрос так, как его
   сформулировало бы предприятие. Например:
   - «производим прицепы и полуприцепы для легковых автомобилей»;
   - «выпускаем промышленные чиллеры и компрессорно-конденсаторные блоки»;
   - «станки токарные с ЧПУ, как подтвердить российское производство».
2. Если известен **код ОКПД2** — вписать его в отдельное поле (повышает точность).
3. Нажать **«Найти»**. Через несколько секунд появятся:
   - **Анализ** — к какой позиции относится продукция, ключевые требования/баллы, что уточнить;
   - **Найденные позиции 719** — раскрываемые источники (раздел, коды, операции, привязка);
   - **Чек-лист документов**;
   - **Пометка** о предварительном характере ответа.

## Часть 3. Что оценивать

Для каждого кейса эксперт ставит оценку по 5 критериям (да/нет/частично):

| № | Критерий |
|---|---|
| 1 | **Верная позиция/раздел.** Система указала ту позицию приложения, что и эксперт. |
| 2 | **Верные коды ОКПД2.** Коды в источнике соответствуют продукции. |
| 3 | **Корректные требования/баллы.** Операции и баллы приведены без искажений. |
| 4 | **Нет выдумок.** Система не сочинила баллы/операции, которых нет в 719. |
| 5 | **Полезность.** Ответ реально экономит время / даёт верное направление. |

**Считаем кейс «успешным»**, если критерии 1, 3, 4 выполнены (верная позиция, корректные
требования, без выдумок). **Критерий приёмки: ≥ 70% успешных кейсов** из 10.

## Часть 5. Петля обучения — как зафиксировать ошибку или разъяснение

Если эксперт исправил ответ или дал важное разъяснение — его нужно сохранить, чтобы
система учитывала это в будущем (без дообучения модели).

1. Создать файл `knowledge_base/cases/<краткое-имя>.json`, например `chillery.json`:
   ```json
   {
     "query": "как предприятие сформулировало вопрос",
     "okpd2": "28.25.13",
     "section_roman": "X",
     "product_name": "Чиллеры",
     "expert_answer": "Проверенное экспертом разъяснение/исправление.",
     "correction_of": "что AI ответил неверно (если это исправление)",
     "source": "ФИО эксперта, дата"
   }
   ```
   Обязательны только `query` и `expert_answer`. Подробности — в
   `knowledge_base/cases/README.md`.
2. Переиндексировать:
   ```
   .venv\Scripts\python scripts\seed_cases.py
   ```
3. Готово. Похожие запросы теперь получают ответ **с учётом подтверждённого кейса**
   (он имеет высший приоритет). Файл закоммитить в репозиторий.

## Часть 6. Известные ограничения V1 (чтобы не считать багом)

- **Точные пороги/потолки баллов** (особенно методологические абзацы раздела X: потолки
  НИОКР, ступенчатые годовые минимумы) — сохранены, но детальная привязка к продукту —
  задача **V2**. Для навигации (найти группу + ключевые требования) это не критично.
- Система **не выносит вердикт** «российская/не российская» — это решает эксперт.
- Ответ зависит от формулировки запроса: чем конкретнее описание/код, тем точнее.

## Часть 7. Куда сообщать о проблемах

- Технические сбои (не открывается, ошибки в окне) — оператору.
- Содержательные ошибки навигатора — фиксировать кейсом (Часть 5) и/или в протоколе
  (Часть 4), это и есть материал для улучшения.
