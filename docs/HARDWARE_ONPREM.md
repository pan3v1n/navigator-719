## 1. Что сервису реально нужно от железа

Прежде чем выбирать машину, надо понимать профиль нагрузки — он нетипичный и **гораздо легче,
чем кажется по слову «RAG»**.

| Компонент | Где считается | Нагрузка на сервер |
|---|---|---|
| **LLM — DeepSeek V3** | **не у нас**, HTTP-вызов к внешнему API | 0 CPU, 0 VRAM: процесс ждёт сети |
| **e5-large** (`intfloat/multilingual-e5-large`) | локально на CPU, `app/rag/embeddings.py` | ~3–4 ГБ RAM резидентно; **один короткий энкод на запрос** |
| **BM25** (`app/rag/sparse.py`) | локально | mmh3 + стеммер, микросекунды |
| **Qdrant** | Docker-контейнер | корпус ≈1 700 чанков ≈ единицы МБ векторов |
| **FastAPI + SQLite** | локально | десятки запросов в день от 6–17 пользователей |

Отсюда три следствия, определяющие весь выбор железа:

- **Видеокарта не нужна ни в каком виде.** Генерацию делает DeepSeek по сети. GPU понадобился бы
  только при переходе на локальную LLM — это отдельное решение, не раньше прохождения приёмки.
- **Связывающий ресурс — оперативная память**, из-за резидентного e5.
- **Пиковая нагрузка — не запросы, а переиндексация** (`scripts/load_kb.py`): весь корпус через
  e5 батчами по 64 (`ENCODE_BATCH` в `app/rag/embeddings.py`). Рабочий запрос против неё — ничто.

Официальный минимум из [RAG_EXPLAINED.md](RAG_EXPLAINED.md):

| Параметр | Минимум (впритык) | Рекомендуется |
|---|---|---|
| RAM | 4 ГБ | 8 ГБ |
| vCPU | 2 | 4 |
| Диск | 20 ГБ | 30–40 ГБ |

**Ориентир из практики:** боевая VM июльского теста — **2 vCPU / 8 ГБ** ([DEPLOY.md](DEPLOY.md) §3),
и она вытянула тест 17 региональных ТПП.

## 2. Критерии отбора машины

Правила универсальные — годятся и для будущих машин, не только для нынешней кладовой.

### 2.1. Жёсткая отсечка: поддержка AVX2

`app/rag/embeddings.py` гоняет e5-large через PyTorch на CPU. Torch подбирает вычислительные ядра
под набор инструкций процессора:

| Набор инструкций | Пригодность | Примерное время энкода запроса |
|---|---|---|
| **AVX2** | ✅ целевой | ~100–300 мс |
| **AVX** без AVX2 | ⚠️ работает, терпимо | в 2–3 раза дольше |
| **без AVX** | ❌ **не связываться** | либо не импортируется, либо сервис бесполезен |

**Как проверить** — с загрузочной флешки Ubuntu Live на самой машине:

```bash
lscpu | grep -oE 'avx2|avx|fma' | sort -u
```

⚠️ **Главная ловушка офисного парка — Celeron, Pentium и Atom.** Intel отключала AVX на этих
линейках даже в свежих поколениях. Pentium G4560 2017 года выглядит новее, чем Core i5-4590
2013 года, но для нас он непригоден, а i5 — годен.

**Правило:** только Core i3/i5/i7 с номером модели от 4000, либо Ryzen, либо AMD на Excavator
и новее. **Celeron / Pentium / Atom — мимо, независимо от года выпуска.**

### 2.2. Остальные критерии

| Параметр | Не связываться | Рабочий минимум | Цель |
|---|---|---|---|
| **Ядра** | 1 | 2 | 4+ |
| **ОЗУ** | 4 ГБ | 8 ГБ | **16 ГБ** |
| **Каналы памяти** | — | одноканал | **двухканал** (см. §4.2) |
| **Диск** | любой HDD | — | **новый SATA SSD от 240 ГБ** |
| **Корпус** | самосборка неизвестного происхождения | — | брендовый SFF (Lenovo / Dell / HP) |

**Почему брендовый SFF, а не сборка из лучших частей.** Соблазн собрать «лучшее из всего» надо
давить: заводская машина имеет проверенный годами БП, продуманный продув, тихое охлаждение и
нулевую рулетку совместимости. Берём **одну целую машину** и доводим её, а не конструируем
франкенштейна из россыпи.

### 3.1. Профиль Lenovo ThinkCentre M715s

| Параметр | Значение |
|---|---|
| Форм-фактор | SFF, штатный БП Lenovo |
| Плата | Lenovo AM4P2MS, сокет AM4 |
| CPU | AMD PRO A8-8670E (AD867BAHM44AB), 4C/4T, 2.8–3.3 ГГц, TDP 35 Вт |
| Микроархитектура | **Bristol Ridge / Excavator** (2016–2017) |
| Графика | Radeon R7, встроенная |
| Память | **4 × DIMM DDR4-2400 UDIMM non-ECC, до 64 ГБ** |
| Энергопотребление | ~15–25 Вт в простое, 45–60 Вт под нагрузкой → ~100–150 ₽/мес |

**Про AVX2.** Excavator — первое поколение AMD, где появился AVX2, то есть машина проходит
отсечку §2.1. **Проверить это на живой машине обязательно** (Приложение Б — что делать, если
не подтвердится).

**Про «не пригодно для ML» в листе «Рекомендации» инвентаризации.** Для обучения моделей — верно.
**Но Навигатор не делает ML:** он делает один энкод запроса и уходит ждать DeepSeek по сети.
Эта строка машину не дисквалифицирует.

**Про реальный параллелизм.** Excavator — модульная архитектура: **2 модуля, в каждом два
целочисленных ядра и ОДИН общий блок вещественной арифметики**. То есть «4 ядра» = 4 целочисленных
ядра, но **всего 2 FPU**. Инференс e5 — сплошная вещественная арифметика, значит эффективный
параллелизм для нашей нагрузки равен двум. Это не отменяет пригодность (боевая VM была 2 vCPU),
но объясняет, почему индексация пойдёт заметно медленнее, чем на современном ядре.

## 4. Целевая конфигурация сервера

### 4.1. Состав

```
Lenovo ThinkCentre M715s, инв. PC0PHYZ7 (ПК №2)
├── CPU     AMD PRO A8-8670E, 4C/4T, 35 Вт          — штатный
├── ОЗУ     2 × 8 ГБ KEMBONA DDR4-2400, двухканал   — своя + перенос с ПК №3
├── Диск 1  новый SATA SSD 240–256 ГБ               — ПОКУПКА: система + сервис
├── Диск 2  штатный SSD Teelkoou 128 ГБ             — локальные бэкапы БД
├── БП      штатный Lenovo                          — штатный
└── ОС      Ubuntu Server 24.04 LTS headless
```

### 4.2. Почему 2 × 8 ГБ, а не 4 × 8 = 32 ГБ

Планок в кладовой хватает на 32 ГБ, и соблазн понятен. Тем не менее берём 16:

- Планки **разнородные** (KEMBONA + COMPIT) — смешивать в четырёх слотах рискованно;
- контроллер памяти Bristol Ridge при **четырёх** заполненных слотах обычно сбрасывает частоту
  с 2400 до 1866–2133;
- инференс e5 на CPU частично **упирается в пропускную способность памяти**, а не в объём —
  поэтому **две одинаковые планки на 2400 в двухканале быстрее четырёх разнородных на 1866**;
- объём сверх 16 ГБ сервису сегодня девать некуда: боевая VM жила на 8.

**Двухканал здесь важнее объёма.** Сейчас все машины кладовой работают в одноканале, по одной
планке — это режет пропускную способность вдвое. Исправление этого и есть главный прирост,
который вообще можно выжать из данного железа, причём бесплатно.

> Если позже понадобится 32 ГБ (Postgres, расширение корпуса) — доставить пару **одинаковых**
> планок и обязательно прогнать memtest заново.

## 6. Сборка — пошагово

### Шаг 1. Проверить AVX2 (до всего остального)

Загрузиться с флешки Ubuntu Live на **любой** M715s:

```bash
lscpu | grep -oE 'avx2|avx|fma' | sort -u    # ждём avx2
lscpu | grep -E 'Model name|^CPU\(s\)'
free -h
```

- [ ] `avx2` присутствует в выводе

⚠️ **Если `avx2` нет — остановиться и перейти к Приложению Б.** Вся дальнейшая инструкция
исходит из того, что он есть.

### Шаг 2. Подготовить ПК №2 (обслуживание)

- [ ] Снять крышку, продуть от пыли
- [ ] Осмотреть материнскую плату и БП на **вздутые конденсаторы** — вздутый бочонок означает,
      что машина идёт в утиль, берём резерв (ПК №1)
- [ ] Снять старую термопасту с крышки процессора и радиатора, нанести новую
- [ ] **Установить кулер** (по инвентаризации он был снят) — проверить, что защёлки сели и
      вентилятор подключён к разъёму CPU_FAN на плате
- [ ] Заменить батарейку CR2032

### Шаг 3. Память — двухканал

- [ ] Извлечь планку KEMBONA KBN24N17S8/8 из **ПК №3**
- [ ] Установить обе планки KEMBONA в ПК №2 **в правильную пару слотов**

⚠️ **Слоты выбрать по мануалу Lenovo, а не «куда влезло».** На платах с четырьмя слотами
двухканал работает только на определённой паре (обычно одноцветной, дальней от процессора).
Инвентаризация верно насторожилась на записи «память в нижнем синем слоте» — этот момент
надо сверить.

- [ ] После загрузки ОС **убедиться, что двухканал действительно включился**:

```bash
sudo dmidecode -t memory | grep -E 'Size|Locator|Speed|Configured'
```

Ожидаем **две** планки по 8192 MB со скоростью 2400 MT/s.

### Шаг 4. Диски

- [ ] Установить новый SSD 240–256 ГБ — он станет системным
- [ ] Штатный SSD Teelkoou 128 ГБ оставить вторым диском (под бэкапы)
- [ ] Проверить SMART обоих дисков:

```bash
sudo apt install -y smartmontools
sudo smartctl -a /dev/sda | grep -Ei 'Power_On_Hours|Wear|Reallocated|Health'
```

### Шаг 5. Memtest — обязательно, на ночь

- [ ] Один **полный** проход Memtest86+ (есть в меню загрузки Ubuntu Live)

Планки б/у, из разных партий, и раньше работали поодиночке — а теперь встают парой. **Это главный
источник загадочных падений, которые потом неделю ищут в коде.** Один ночной прогон отделяет
«железо годное» от «железо будет вас мучить».

## 7. Настройки BIOS — три пункта, про которые забывают

| Настройка | Значение | Почему это важно |
|---|---|---|
| **After Power Loss** | **Power On** | По умолчанию после отключения света машина останется выключенной, а в выходные в кладовую никто не пойдёт. Для сервера пункт обязательный |
| **Дата и время** | выставить верно | Вместе со свежей батарейкой CR2032 |
| **Boot order** | новый SSD первым | Чтобы не грузилось со второго диска |

⚠️ **Про батарейку и часы — не мелочь.** Севшая CR2032 = сбитые часы при каждом обесточивании.
Дальше перестают сходиться подписанные сессионные куки (`itsdangerous`, `SESSION_SECRET`),
ломается валидация TLS-сертификата, едут даты в `messages`. Симптом выглядит как «пользователей
случайно разлогинивает», а причина — деталь за сто рублей. **После установки ОС обязательно
включить синхронизацию времени:**

```bash
sudo timedatectl set-timezone Europe/Moscow
sudo timedatectl set-ntp true
timedatectl status          # ждём "System clock synchronized: yes"
```

## 8. ОС и развёртывание

### 8.1. Почему Ubuntu Server headless, а не Windows

Графическая оболочка тут не нужна и только съедает память. Ubuntu Server без графики живёт
в ~500 МБ против 2–3 ГБ у Windows. Заодно совпадает с тем, что описано в [DEPLOY.md](DEPLOY.md),
и `docker-compose.yml` из репозитория ложится без единой правки.

- [ ] Ubuntu Server 24.04 LTS, минимальная установка, **системный диск — новый SSD**
- [ ] Включить OpenSSH при установке
- [ ] Второй диск смонтировать в `/backup`

### 8.2. Swap — страховка от OOM

На 16 ГБ это скорее подстраховка, но пиковый момент (`load_kb.py` держит батч из 64 чанков)
лучше пережить со swap, чем с убитым процессом:

```bash
sudo fallocate -l 8G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

### 8.3. Развёртывание

**Шаги 1–4 из [DEPLOY.md](DEPLOY.md) не нужны** — они про установку `yc` CLI, сеть Яндекса и
создание VM. **Начиная с установки Docker и `docker compose up` инструкция работает как есть**,
потому что артефакты развёртывания провайдеро-независимы: `Dockerfile`, `docker-compose.yml`,
`.dockerignore` лежат в корне репозитория.

```bash
sudo apt update && sudo apt install -y docker.io docker-compose-v2 git
sudo usermod -aG docker $USER      # перелогиниться

git clone https://github.com/pan3v1n/navigator-719.git && cd navigator-719
cp .env.example .env
```

- [ ] Заполнить `.env`: `DEEPSEEK_API_KEY`, `QDRANT_URL`, **`SESSION_SECRET`**
      (в проде приложение не стартует с дефолтным)
- [ ] Сверить чек-лист редеплоя — [REVIEW_TZ.md](REVIEW_TZ.md) §1а, там же предупреждение
      про новые файлы данных, которые должны попасть в архив деплоя

```bash
docker compose up -d
docker compose run --rm app python scripts/load_kb.py
```

> **Про скачивание e5.** Первый `load_kb` тянет модель (~2 ГБ) с HuggingFace, и на рваной сети
> это рвётся. `hf_xet` уже в `requirements.txt` (чанковая докачка). Запасные пути — зеркало
> `HF_ENDPOINT=https://hf-mirror.com` или ручная папка `models/` с абсолютным путём в
> `EMBEDDING_MODEL`. Подробно — `SETUP.md`, Шаг 5.

## 9. Приёмка железа

Два теста, оба обязательны.

### Тест 1. Memtest86+ — один полный проход (см. §6, Шаг 5)

### Тест 2. Настоящая приёмка — пиковой нагрузкой самого сервиса

```bash
time docker compose run --rm app python scripts/load_kb.py
```

Это и есть честный бенчмарк: весь корпус (≈1 700 чанков) через e5-large батчами по 64.
**Тяжелее сервис не делает ничего и никогда.**

| Результат | Вывод |
|---|---|
| Прошло без падения по памяти | ✅ **машина принята** — рабочий запрос против индексации ничто |
| Убито по OOM | Проверить swap (§8.2), проверить что памяти действительно 16 ГБ |
| Ощутимо дольше получаса | См. тюнинг ниже |

**Ожидание: 15–30 минут** — против единиц минут на современном ядре. Причина в §3.1: два FPU
на четыре ядра. Это оценка, а не замер; проверится ровно этим запуском.

**Если индексация окажется мучительно долгой.** В `app/rag/embeddings.py` вызов
`torch.set_num_threads(os.cpu_count())` берёт все 4 потока, а блоков вещественной арифметики
всего два — потоки будут конкурировать. Стоит замерить, не быстрее ли на двух. Это оптимизация,
а не блокер: на скорость обслуживания запросов почти не влияет.

## 10. Резерв и обслуживание

### 10.1. Схема резерва

| Машина | Роль | Состояние хранения |
|---|---|---|
| **ПК №2 PC0PHYZ7** | боевой сервер | в работе |

**Процедура при отказе сервера:** переставить оба SSD в ПК №1, переставить пару планок,
включить. Машины идентичные — ОС загрузится без переустановки. Ориентировочно 20 минут.

- [ ] **Снять серийные номера с ПК №3–6** (в инвентаризации не зафиксированы) — иначе резерв
      нельзя корректно провести по учёту

|---|---|

### ПК №7, самосборка СБ/054909-170718-3 — **не подходит**

| Причина | Детали |
|---|---|
| **Нет AVX вообще** | Celeron J1800 — микроархитектура Bay Trail: есть SSE4.2, но **ни AVX, ни AVX2**. PyTorch на нём либо не стартует, либо работает так, что сервис бесполезен. Это отсечка §2.1 в чистом виде |

(AdGuard Home, Tailscale-нода). Для этого он вполне хорош.

## Приложение Б. Если AVX2 не подтвердится

Порядок действий, если `lscpu` на M715s не покажет `avx2`:

1. **Проверить, что есть хотя бы `avx`.** Если да — машина условно годна, просто индексация
   пойдёт в 2–3 раза дольше. Прогнать Тест 2 (§9) и решать по факту.
2. **Поискать в ТПП другое железо** по критериям §2: Core i3/i5/i7 от 4000-й серии
   (Dell OptiPlex 3020/7020/9020, HP EliteDesk 800 / ProDesk 600, Lenovo ThinkCentre M83/M93).
3. **Снизить требования сменой эмбеддера** — крайняя мера, платится качеством поиска:
   `EMBEDDING_MODEL=intfloat/multilingual-e5-base` (влезает в 4 ГБ, ретрив чуть хуже).
   Обоснование и альтернативы — [RAG_EXPLAINED.md](RAG_EXPLAINED.md).
4. **Купить мини-ПК** на Ryzen 7 5825U / 7735HS, 32 ГБ, 1 ТБ — 35 000–50 000 ₽,
   15–30 Вт, бесшумный. Запасной вариант, если из имеющегося не выходит ничего.

## Приложение В. Чего этот сервер НЕ решает

Железо закрывает вопрос вычислений, но не закрывает эксплуатацию. Что остаётся решить отдельно:

| Вопрос | Комментарий |
|---|---|
| **Доступ извне сети ТПП** | Нужен белый IP и проброс 80/443 через IT ТПП. **Но для контрольной волны тестирования это не блокер:** экспертам внутри сети ТПП сервис доступен сразу |
| **HTTPS** | Домен + Let's Encrypt; требует открытых 80/443 |
| **Внешние бэкапы** | Второй диск не спасёт от пожара, залива и кражи |
| **Резервный канал связи** | При обрыве интернета DeepSeek недоступен → сервис не отвечает |

**Важное следствие:** машину можно ввести в строй и начать контрольную волну **до** решения
вопросов с белым IP и сертификатом. Это отвязывает тестирование от инфраструктурной возни.
