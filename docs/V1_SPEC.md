## 1. Что такое V1 простыми словами

V1 — это **умный поисковик-консультант по Постановлению №719**.

Сотрудник предприятия или эксперт ТПП пишет в свободной форме:
> «Производим прицепы для легковых автомобилей, код ОКПД2 29.20.23»

Система:
1. Понимает, о каком товаре речь.
2. Находит в приложениях к ПП №719 нужный раздел и конкретный вид продукции.
3. Показывает: какой **тип требования** применяется (баллы / перечень операций / процент),
   какой **минимальный порог**, какие **ключевые операции** нужно выполнять в РФ.
4. Даёт **ссылку на источник** — конкретный пункт постановления.
5. Помечает ответ как **предварительный** — требующий проверки экспертом ТПП.

**Что V1 НЕ делает** (это V2–V3):
- не проверяет загруженные документы предприятия;
- не считает фактически набранные баллы по документам;
- не генерирует акты экспертизы.

V1 = **навигация и консультация по тексту закона**. Это фундамент, на котором строится всё остальное.

## 2. Зачем это нужно (ценность для ТПП)

| Проблема сегодня | Что даёт V1 |
|---|---|
| Эксперт вручную ищет нужный раздел в 200+ страницах постановления | Поиск за секунды по смыслу, а не по Ctrl+F |
| Предприятие не понимает, под какой пункт попадает товар | Понятная карточка с требованиями и порогом |
| Постоянные правки 719 (десятки редакций в год) | Один раз переиндексировали — актуально для всех |
| Типовые вопросы отнимают время эксперта | Предварительный ответ генерируется автоматически |

**Бизнес-эффект:** снижение нагрузки на экспертов, ускорение первичной консультации предприятий,
единая база знаний вместо «знаний в голове конкретного сотрудника».

## 3. Технологический стек V1

Весь стек — **доступен из РФ**, без заблокированных сервисов.

| Слой | Технология | Версия | Почему |
|---|---|---|---|
| **LLM** | DeepSeek V3 (`deepseek-chat`) | API | Доступен из РФ напрямую, дёшево (~$0.14/1M токенов), хорошо понимает русский и юридический текст |
| **Embeddings** | `intfloat/multilingual-e5-large` | локально | Лучшее качество на русском, работает офлайн через `sentence-transformers`, без внешних API |
| **Vector DB** | Qdrant | self-hosted Docker | Open source, РФ-доступен, поддерживает гибридный поиск (dense + sparse) |
| **RAG-оркестрация** | рукописный (qdrant_client + sentence-transformers) | — | LlamaIndex НЕ используется — RAG собран вручную (RF-first, контроль над антигаллюцинациями). Историческая запись спека, см. CLAUDE.md |
| **Backend** | FastAPI | 0.115+ | Async, автодокументация Swagger, стандарт индустрии |
| **Frontend MVP** | Streamlit | 1.39+ | Быстрый UI на Python, без отдельного фронтенд-разработчика |
| **Хранение данных** | SQLite | — | Логи запросов, кейсы экспертов (в V2 → PostgreSQL) |
| **Парсинг исходника** | striprtf | 0.0.32 | Уже использован в V0 для RTF → текст |

### Почему именно гибридный поиск (dense + sparse)

Запросы содержат два разных типа информации:
- **Смысловое описание** товара («прицепы для легковых авто») → хорошо ловит **dense**-вектор (семантика).
- **Точные коды** ОКПД2/ТН ВЭД («29.20.23») → числовые токены, по которым семантика плохо работает,
  но отлично работает **sparse**-поиск (BM25-подобный, по точному совпадению).

Гибрид объединяет оба через **Reciprocal Rank Fusion (RRF)** — повышает точность нахождения нужного вида продукции.

## 5. Как это работает: поток данных по шагам

### Шаг 0 — Подготовка базы знаний (разово, скрипт `load_kb.py`)

Текущие чанки из V0 — это **целые разделы** (раздел III = 757 КБ). Для RAG это слишком крупно:
в один контекст не влезет, поиск неточный. Нужна **структуризация на уровне отдельных видов продукции**.

**Подзадача 1.1 — структурный парсинг приложений.** Каждый раздел приложения содержит таблицу видов
продукции. Один вид = один чанк. Стратегия извлечения:

1. **Регулярки** делят раздел на кандидатов-записей (по номерам позиций, названиям, кодам ТН ВЭД).
2. **DeepSeek в режиме JSON** нормализует «грязный» текст записи в структуру:
   ```json
   {
     "section_roman": "II",
     "section_title": "Продукция автомобилестроения",
     "product_name": "Прицепы и полуприцепы для легковых автомобилей",
     "okpd2_codes": ["29.20.23"],
     "tnved_codes": ["8716"],
     "requirement_type": "points",        // points | operations | percentage
     "min_threshold": "не менее 1000 баллов с 2024 г.",
     "key_requirements": ["сварка рамы", "окраска", "сборка"],
     "source_anchor": "Раздел II, позиция 5"
   }
   ```
3. Структурированные записи сохраняются в `knowledge_base/pp719/structured/*.json`
   (под версионный контроль — чтобы не перепарсивать каждый раз).

> Парсинг через LLM — разовая батч-операция. ~Несколько сотен записей × дешёвый DeepSeek =
> символическая стоимость. Результат коммитится в репозиторий.

**Подзадача 1.2 — индексация в Qdrant.** Для каждой структурированной записи:
- текст для эмбеддинга = `product_name + key_requirements + коды`;
- dense-вектор через e5-large (1024 измерения);
- sparse-вектор (BM25) по тому же тексту;
- payload = вся структура из JSON выше.

### Шаг 1 — Пользователь отправляет запрос

```
POST /navigate
{ "query": "производим прицепы для легковых авто", "okpd2": "29.20.23" }
```

### Шаг 2 — Предобработка (navigator.py)

- Если код ОКПД2 не передан явно — пытаемся извлечь его из текста регуляркой
  (`\d{2}\.\d{2}(\.\d{2})?`).
- Нормализуем текст запроса (для e5 добавляется префикс `query: ` — требование модели).

### Шаг 3 — Гибридный поиск (retriever.py)

1. Dense-поиск по семантике запроса.
2. Sparse-поиск по ключевым словам и кодам.
3. Если есть код ОКПД2 — **жёсткий фильтр/буст** записей с совпадающим префиксом кода.
4. RRF-слияние результатов → **top-5** наиболее релевантных записей.
5. Параллельно — поиск в коллекции `verified_cases` (ответы, подтверждённые экспертом):
   если есть близкий проверенный кейс, он идёт в контекст с **высшим приоритетом**.

### Шаг 4 — Генерация ответа (pipeline.py + DeepSeek)

В DeepSeek уходит:
- **системный промпт** (роль ассистента эксперта ТПП, правила, формат);
- **контекст** — top-5 записей + проверенные кейсы;
- **запрос пользователя**.

DeepSeek возвращает **структурированный JSON**:
```json
{
  "found": true,
  "section": "Раздел II. Продукция автомобилестроения",
  "product_match": "Прицепы и полуприцепы для легковых автомобилей",
  "requirement_type": "Балльная система",
  "min_threshold": "не менее 1000 баллов (с 1 января 2024 г.)",
  "key_requirements": [
    "сварка рамы на территории РФ",
    "окраска кузова",
    "сборка готового изделия"
  ],
  "source": "Приложение к ПП №719, Раздел II, позиция 5",
  "confidence": "высокая",
  "notes": "Уточните год — пороги баллов менялись редакциями постановления"
}
```

### Шаг 5 — Постобработка и дисклеймер

navigator.py **всегда** добавляет в ответ обязательное поле:
```json
"disclaimer": "⚠️ Предварительный анализ ИИ. Окончательное заключение даёт уполномоченный эксперт Курской ТПП."
```

### Шаг 6 — Отображение (Streamlit)

UI рисует карточку результата: раздел, вид продукции, тип требования, порог, ключевые операции,
ссылку на источник, дисклеймер и кнопку «Сообщить об ошибке эксперту».

## 6. Системный промпт (app/core/prompts.py)

Ключевые принципы промпта:

```
Ты — ассистент эксперта Курской торгово-промышленной палаты по Постановлению
Правительства РФ №719 о подтверждении производства российской промышленной продукции.

ТВОЯ ЗАДАЧА: по описанию товара и предоставленному контексту из текста постановления
определить применимый раздел приложения, вид продукции и требования.

ЖЁСТКИЕ ПРАВИЛА:
1. Отвечай ТОЛЬКО на основе предоставленного контекста. Если в контексте нет ответа —
   честно скажи «не найдено в предоставленных данных», не выдумывай.
2. Никогда не давай окончательного юридического заключения. Ты — помощник, вердикт за экспертом.
3. Всегда указывай источник (раздел, позицию приложения).
4. Если данные в контексте противоречивы или зависят от года/редакции — отметь это в notes.
5. Отвечай строго в формате JSON по заданной схеме.
```

## 8. Петля обучения от эксперта (ключевая фишка)

Это то, что отличает продукт от «просто чатбота» и снимает опасение вице-президента про «осторожность с ИИ».

```
Эксперт видит ответ ИИ
        │
        ├─ ✅ Верно  ──► запись в verified_cases (повышает приоритет в будущем)
        │
        └─ ❌ Ошибка ──► эксперт вписывает правильный ответ
                          │
                          ▼
                  knowledge_base/cases/case_NNN.json
                          │
                  scripts/seed_cases.py (переиндексация)
                          │
                          ▼
                  коллекция verified_cases в Qdrant
                          │
                  при следующем похожем запросе —
                  проверенный ответ идёт в контекст с высшим приоритетом
```

Точность растёт **без дообучения модели** — просто за счёт накопления проверенных кейсов в базе.
Каждый кейс — это пара «запрос → правильный ответ эксперта», подтверждённая человеком.

## 13. Риски и как их снижаем

| Риск | Вероятность | Снижение |
|---|---|---|
| Структурный парсинг приложений неточен (текст «грязный» после RTF) | Высокая | LLM-нормализация + ручная проверка экспертом первых записей |
| e5-large тяжёлый, медленно на слабом железе | Средняя | Альтернатива — `multilingual-e5-base` (легче); эмбеддинги кешируются |
| DeepSeek галлюцинирует требования, которых нет в 719 | Средняя | Жёсткий промпт «только из контекста» + дисклеймер + петля эксперта |
| Пороги баллов зависят от года/редакции | Высокая | Модель обязана отмечать это в `notes`; финальное слово за экспертом |
| Запросы с нечётким описанием товара | Средняя | Гибридный поиск + уточняющие вопросы в чат-режиме |
