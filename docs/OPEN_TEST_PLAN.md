   процедурный интент** → статистика «что эксперты спрашивают» приоритизирует корпус Правил (P2).

## P0 — Обратная связь v2

> **Правки заказчика 2026-07-05:** оценка ответа = **звёзды 0–5** (не 👍/👎); на диалог с экспертом —
> **комментарий**; **глобальная форма обратной связи на весь сервис — остаётся как есть**. Полноценной
> таблицы `Correction`, очереди промоута и `Conversation` НЕ нужно — но **оставляем простое опц. поле
> «исправление»** на ответе (эксперт отмечает критическую ошибку; просто хранится, без автоматизации петли).
>
> **✅ ВЫПОЛНЕНО 2026-07-05.** Итоговая форма (правки по ходу): на каждом ответе — компактная ссылка
> **«Оценить ответ»** (раскрывает звёзды 0–5 + комментарий к этому ответу) · **«отметить ошибку»**
> (исправление) · **«комментарий к диалогу»**; глобальная форма без изменений. Единая `Feedback`+`kind`
> ('answer'|'dialog'|'service') + `session_id`/`message_id`/`correction` (ALTER-миграция, легаси-отзывы →
> `service`); `/api/chat` отдаёт `message_id`. Админ-скоркарта: «Приёмка ответов» (%≥4★) + звёзды
> (avg+распределение) + исправления + комментарии к ответам/диалогам. **Стартовая страница админа → чат**
> (дашборд из сайдбара). Проверено: **44 юнит-теста** + **e2e TestClient 18/18**.

**Зачем:** сегодня фидбек — один глобальный «отзыв в конце сессии», привязан только к пользователю
(нет `message_id`/`session_id`) → по нему **нельзя посчитать %-приёмку по ответам** и нельзя понять,
какой именно ответ оценён. Добавляем привязку оценок/комментариев/исправлений к ответу/диалогу;
глобальную форму сохраняем без изменений.

**Каналы фидбека:**
1. **Оценка ответа** — **звёзды 0–5** на каждом assistant-пузыре, клик = оценка (привязка к `message_id`).
   - **опц. «исправление»** — если эксперт заметил КРИТИЧЕСКУЮ ошибку: поле для правильного ответа/пометки
     (тоже к `message_id`). Просто хранится (без авто-промоута в `verified_cases`; вручную офлайн после теста).
2. **Комментарий к диалогу** — свободный текст по беседе (привязка к `session_id`); доступен по ходу и
   при «Завершить диалог».
3. **Глобальная форма сервиса** — существующая (оценка 1–5 + соответствие да/частично/нет + текст),
   **без изменений** (сайдбар «Оставить отзыв»).

**Модель данных** (`app/db/models.py`, ALTER-миграция в `init_db`/`engine.py` как для токенов):
- Единая таблица `Feedback` с дискриминатором `kind`:
  `user_id, ts, kind ('answer'|'dialog'|'service'), session_id (nullable), message_id (FK, nullable),
  rating (nullable, 0–5), matched (nullable — только 'service'), comment (nullable), correction (nullable)`.
  - `kind='answer'`: `message_id` + `session_id` + `rating` (звёзды 0–5) + опц. `correction`.
  - `kind='dialog'`: `session_id` + `comment`.
  - `kind='service'`: `rating` (1–5) + `matched` + `comment` — существующая глобальная форма, путь не меняется.
- Таблицы `Correction`/`Conversation` НЕ создаём — упрощено по правке заказчика.

**API** (`app/api/web.py`):
- Расширить `POST /api/feedback`: +`kind`, +`session_id`, +`message_id`, +`correction`, `rating` (0–5).
  Существующий путь глобальной формы (`kind='service'`, без `message_id`) работает как раньше.
- Валидация: `rating` 0–5; `message_id` обязателен при `kind='answer'`; `session_id` — при `kind='dialog'`.
- В `POST /api/chat` (`ChatResponse`) **вернуть `message_id`** сохранённого ответа — иначе клиенту нечем
  привязать звёзды/исправление к реплике.

**UI** (`app/web/static/chat.js` + `templates/chat.html`):
- На каждом assistant-пузыре — **строка из 5 звёзд (0–5)** + ссылка **«отметить ошибку / исправление»**
  (раскрывает textarea) → POST `kind='answer'` с `message_id` (+`correction`).
- **«Комментарий к диалогу»** (поле/кнопка, в т.ч. на «Завершить диалог») → POST `kind='dialog'` с `session_id`.
- **Глобальная форма** в сайдбаре — как есть.
- **Переиспользуем** паттерн модалка+POST (`chat.js:384-404`) и поля `rating`/`comment`.

**Админ-скоркарта** (`/admin`):
- **Средние звёзды** по эксперту и суммарно + распределение оценок 0–5 (per-answer) = сигнал качества.
- **Комментарии к диалогам** и per-answer оценки, привязанные к веткам беседы (сейчас детачнуты).
- **Исправления** (критические ошибки) — выделять отдельно (высший сигнал; вручную → `verified_cases` после теста).
- Глобальная форма (соответствие да/частично/нет) — как сейчас.
- **ЕДИНЫЙ ГЕЙТ (зафиксирован, синхронно с `docs/TESTING.md`):** доля ответов с оценкой **≥4★ ≥70%**
  (KPI «Приёмка ответов» в `/admin` считает автоматически). Отдельно мониторим флаг незаземлённых
  чисел (пометка «Проверьте показатели» / счётчик в /admin) — должен быть ≈0.

ОБЕЩАЕТ follow-up'ы («можно уточнять: „а какой порог?"») — расхождение обещания и поведения.

**Точки вставки (из разведки кода):**
1. **Транспорт** (`app/api/chat.py`): грузить прошлые реплики по `session_id` (`q.get_session_messages`

2. **Переписывание запроса ПЕРЕД гейтами** (критично): bare «а какой порог?» без якоря → достроить из
   истории (перенести продукт/ОКПД2 прошлого хода), иначе `meta`/`procedural`/`search` работают на
   контекст-фри запросе. Лёгкий LLM-rewrite ИЛИ детерминированный перенос последнего продукта/кода.
3. **Движок** (`app/rag/pipeline.py`): `answer(query, okpd2, history=...)`; вставить прошлые ходы в
   `messages=[system, …история, user]` (точка — `pipeline.py:220-223`).
4. **UI**: клиент уже шлёт `session_id`; опц. индикатор «продолжение диалога».
