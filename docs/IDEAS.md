# IDEAS — бэклог идей и гипотез по доработке Навигатора ПП №719

> Свалка идей по улучшению сервиса по всем слоям: LLM, RAG, данные, бэкенд, фронт,
> качество, инфраструктура. Это **не план** (формальные фазы и статусы — в
> [../ROADMAP.md](../ROADMAP.md)), а место «записать, пока не забыл». Когда идея созрела
> и принята в работу — переносим её в ROADMAP соответствующей версии (V2/V3/…) и здесь
> помечаем `→ ROADMAP`.

## Как пользоваться
- Кидай идею в нужный раздел. Не бойся дублей и «сырых» формулировок — лучше записать.
- Формат записи (по возможности):
  - **Что** — суть идеи в одну строку.
  - **Зачем** — какую боль решает / что улучшает.
  - **Как** — набросок реализации (если есть). Необязательно.
  - метки: приоритет `P0/P1/P2`, статус, область.
- Статусы: `💡 идея` · `🔬 обдумываем` · `✅ принято → ROADMAP` · `❌ отклонено` · `🧊 заморожено`
- Приоритет: `P0` критично · `P1` важно · `P2` приятно иметь.

## 🤖 LLM (DeepSeek, промпты)
- **Протечка иероглифов в ответе DeepSeek.** `P2` · `💡 идея`
  - **Зачем:** DeepSeek изредка вставляет китайские токены в русский ответ (наблюдали
    `咨询服务` в ответе на «юридические услуги» при тесте out-of-scope guard). Для
    госинструмента Курской ТПП непрофессионально.
  - **Как (по возрастанию надёжности):** (1) усилить в `NAVIGATOR_SYSTEM_PROMPT` требование
    «отвечай ИСКЛЮЧИТЕЛЬНО на русском, латиница только в кодах/терминах»; (2) лёгкий
    постпроцессинг ответа — детект CJK-диапазона (`一-鿿`) и перегенерация/зачистка;
    (3) понизить вероятность через явные few-shot. Редкое, не блокер — но дёшево прикрыть.
  - **Файлы:** `app/core/prompts.py` (`NAVIGATOR_SYSTEM_PROMPT`), `app/rag/pipeline.py`
    (`_ensure_disclaimer` рядом — там же можно чистить ответ).
- **Качество парсинга базы: DeepSeek достаточен; Opus — точечно офлайн на сложных краях.** `P2` · `🔬 обдумываем` (обсуждали 2026-07-03)
  - **Что:** держать DeepSeek дефолтным парсером (`structure_kb.normalize_product`), а сильную
    модель (Opus — доступна прямо в дев-среде Claude Code) применять ТОЧЕЧНО офлайн для сверки на
    структурно-сложных МАЛЫХ разделах и вариант-группах «Из N».
  - **Почему НЕ менять весь пайплайн:** задача LLM узкая — **нормализация уже нарезанного** текста
    одного продукта в JSON. Риск-части детерминированы регексом, НЕ LLM: коды ОКПД2 (`OKPD2_RE`) и
    сегментация (`parse_section`); пустой блок → `empty_stub` без вызова LLM. **Все крупные дефекты
    данных (63 потерянных «Из N», склейка XI–XXIX, «Из») были в РЕГЕКС-сегментаторе, а не в
    галлюцинациях DeepSeek.** Спот-чек фиделити (Круги шлифовальные 23.91.11.140) — 6/6 операций+баллов
    точно. A/B Opus vs DeepSeek (XIV/XIX): DeepSeek дословно верен; Opus выигрывает лишь на
    вариант-группах (различение «член группы» vs «исключённая позиция»).
  - **RF-first нюанс:** парсинг — **офлайн build-step, НЕ рантайм** → RF-ограничение рантайма
    (только DeepSeek) на него НЕ распространяется → Opus офлайн допустим. Рантайм-ответы остаются на
    DeepSeek (RF-доступен, 152-ФЗ).
  - **Рычаг качества — harness, не модель:** `verify_structured` (состав) + `reconcile_kb` (сверка по
    кодам) ловят ошибки любой модели. Гонять при любом парсере.
  - **Когда сильная модель важнее:** под калькулятор (Уровень 2) схема сложнее — структурировать
    пороги по годам, obligatory/optional, взаимоисключающие ветки — там Opus офлайн окупается больше,
    чем на нынешней плоской нормализации.
  - **Файлы:** `scripts/structure_kb.py`, `scripts/verify_structured.py`, `scripts/reconcile_kb.py`.

## 🔎 RAG (поиск, ретрив, эмбеддинги, Qdrant)
- **Out-of-scope guard: отсекать запросы вне сферы 719.** `P1` · `🔬 обдумываем`
  - **Зачем:** на продукции вне 719 (напр. «хлебобулочные изделия») поиск без порога
    релевантности возвращает «ближайший мусор» (наблюдали выдачу «Микрофоны,
    громкоговорители…»). Сейчас заглушка «не найдено» срабатывает только при полностью
    пустом списке, а Qdrant на непустой коллекции всегда что-то отдаёт.
  - **Как (черновик, по возрастанию надёжности):**
    1. Порог по dense-сходству top-1 (косинус e5), а **не** по RRF-score (RRF —
       `1/(k+rank)`, несравним между запросами). Ниже порога → «вне сферы 719/уточните».
    2. Инструкция в `NAVIGATOR_SYSTEM_PROMPT`: если контекст не соответствует продукции —
       прямо сказать «позиция не найдена», не выдумывать.
    3. Комбинация 1+2 (рекомендуется) + быстрый тест на нерелевантный запрос.
  - **Файлы:** `app/rag/retriever.py:112` (search), `app/rag/pipeline.py:85` (ветка «не
    найдено»), `app/core/prompts.py`.

- ### 📈 План улучшения RAG по стадиям (0–5) `🔬 обдумываем`
  > Порядок = приоритет. Принцип: **сначала измеримость, потом точность, потом масштаб.**
  > Обоснование текущей архитектуры и подробный разбор — в [RAG_EXPLAINED.md](RAG_EXPLAINED.md).
  > Каждое улучшение проверяем числом на харнесе из стадии 0, а не «на глаз».

  - **Стадия 0 — Eval-харнес (метрика качества ретрива).** `P0` · предусловие всего ⚠️ делать ПЕРВЫМ
    - **Что такое eval-харнес:** автоматический «экзамен» для поиска. Это (1) **golden set** —
      список пар «запрос → правильная позиция/раздел 719» (эталон, размечает человек/эксперт);
      (2) **прогонщик** — скрипт, который гоняет каждый запрос через `retriever.search` и
      сравнивает выдачу с эталоном; (3) **метрики** — числа, отражающие качество:
      - **recall@k** — доля запросов, где правильная позиция попала в топ-k (нашли ли вообще);
      - **MRR** (Mean Reciprocal Rank) — насколько высоко стоит правильный ответ (1.0 = всегда
        первый; 0.5 = в среднем второй) — отражает качество ранжирования;
      - **hit-rate / precision@k** — точность верхушки выдачи.
    - **Зачем:** сейчас есть только smoke-тесты (4 запроса «на глаз»). Любая правка ниже (порог,
      реранкер, веса RRF) без метрики = **гадание**. Харнес даёт «точку отсчёта» и позволяет
      сказать «правка X подняла recall@5 с 0.78 до 0.91» вместо «вроде стало лучше».
    - **Как:** превратить `docs/test_cases.*` (12 кейсов) в стартовый golden set, расширить до
      ~30–50 (29 разделов + out-of-scope), скрипт `scripts/eval_retrieval.py` → таблица метрик.
      _Сделано 2026-06-18: `scripts/eval_golden.json` (46 кейсов) + `scripts/eval_retrieval.py`._
    - **Цена/риск:** низкая, чистый код, без новых зависимостей. **Максимальный рычаг.**

  - **Стадия 1 — Out-of-scope guard.** `P1` — см. отдельную запись выше (порог dense top-1 +
    инструкция в промпте). Калибруется на харнесе из стадии 0. Самый быстрый честный выигрыш.

  - **Стадия 2 — Реранкер (cross-encoder).** `P1` · `🔬`
    - **Что:** после гибрида (top-20) добавить переранжирование cross-encoder'ом (смотрит пару
      «запрос+кандидат» целиком, точнее bi-encoder) → топ-5 берём из переранжированного.
    - **Качество:** заметный прирост precision@k, когда верный ответ в top-20, но не в top-5.
    - **Риск/условия:** ещё одна модель в RAM + скачивание (RF/DPI). Брать малый мультиязычный
      реранкер (BGE-reranker-base / jina-multilingual), провижнить как e5 (локальная папка).
      Замерить выигрыш на харнесе — если мал, не тащить.

  - **Стадия 3 — Тюнинг гибрида + обработка запроса.** `P2` · `🔬`
    - RRF `k`, prefetch-limit, баланс dense/sparse — подобрать на golden set.
    - **Query expansion** (разговорное→регламентное, словарь синонимов) или **HyDE** (LLM генерит
      гипотетическое описание по короткому запросу → эмбеддим его) — лечит короткие запросы.

  - **Стадия 4 — Гранулярность parent/child (ближе к V2).** `P2` · `🔬`
    - **Проблема:** мега-продукты усекаются до 12 операций в контексте (`MAX_OPS_PER_HIT`).
    - **Что:** индексировать на уровне блоков операций (child), в контекст подтягивать
      родительский продукт (small-to-big / auto-merging). Точка решения «вернуть LlamaIndex
      (готовые parent-retrievers) или дописать руками».

  - **Стадия 5 — Эволюция эмбеддера (по мере роста).** `P2` · `🔬`
    - **BGE-m3** — одна модель: dense + sparse + ColBERT-мультивектор (Qdrant поддерживает
      late interaction) → выше precision ценой хранилища; может заменить e5 + ручной BM25.
    - **Дообучение/адаптация e5** на подтверждённых кейсах эксперта (петля уже готова), когда
      кейсов накопится достаточно.

  - **Сводка приоритетов:** 0 (харнес, сейчас) → 1 (guard) → 2 (реранкер) / 3 (тюнинг) → 4 (V2) → 5 (потолок).
  - **Связанное:** расхождение доки↔код — в `CLAUDE.md` стек заявляет **LlamaIndex**, но RAG
    рукописный (qdrant_client + sentence_transformers напрямую). Привести стек-таблицу в
    соответствие ИЛИ осознанно вернуть LlamaIndex на стадии 4.

- **Оффлоуд эмбеддингов на Yandex Text Embeddings API (разгрузка RAM/CPU VM при масштабе).** `P2` · `🧪 ГИПОТЕЗА — вернуться при масштабе` (обсуждали 2026-07-03)
  - **Гипотеза юзера:** заменив локальный e5-large на Yandex Text Embeddings (doc/query), сэкономим
    RAM сервера и улучшим стабильность при наплыве пользователей.
  - **RAM — ✅ ДА, сильно.** e5-large = **2.1 ГБ весов** (`model.safetensors`, fp32) в RAM + torch-рантайм;
    грузится singleton (`embeddings.py:_model`, `lru_cache`). Снятие освобождает ~2.5–3 ГБ RAM, убирает
    torch из образа (CPU-wheel большой), 2.1 ГБ `models/` с диска и флэки-скачку с HF. На 8 ГБ VM — ~половина
    футпринта app.
  - **Стабильность при масштабе — 🟡 ЧАСТИЧНО.** Убирает CPU-контеншн: e5 forward на 2 vCPU — точка
    сериализации при конкурентных запросах; оффлоуд → app становится I/O-bound (ждёт HTTP) → больше
    одновременных юзеров на тех же ядрах. **НО доминирующий per-request потолок — генерация DeepSeek
    (~секунды), она уже внешняя и оффлоудом эмбеддинга НЕ снимается.** Меняем свой CPU-контеншн на
    зависимость от Yandex rate-limit/латентности/сети в горячем пути.
  - **Serverless, НЕ инстанс:** тарификация по токенам; аренда «модельного инстанса» НЕ нужна.
    Асимметрия doc/query ложится на наш `embed_passages`/`embed_query`.
  - **Цена свапа (важно!):** полная **реваридация** — recall@1 0.972 и F1-идентичность сняты на e5;
    порог out-of-scope guard **`RELEVANCE_SOFT=0.83` откалиброван на КОСИНУСЫ e5** → другой эмбеддер
    ломает guard, пока не перекалибруешь; **Qdrant recreate** (иная размерность vs 1024); +50–200 мс/запрос
    сеть; новый рантайм-хвост (нужен retry/fallback); данные уходят на векторизацию (в РФ/Yandex, 152-ФЗ ок;
    e5 локально — данные не покидают VM).
  - **Дешевле-локальные альтернативы разгрузки RAM (прежде чем в API):** e5 в **fp16** (~1.1 ГБ, почти без
    потерь) или **e5-base** (~1.1 ГБ, 768d — см. Инфра-запись про удешевление, качество мерить).
  - **Когда:** НЕ сейчас (1.0 = ≤6 юзеров, e5 локально ок; «наплыв 100+» — это ROADMAP 4.x). Делать
    **измеримым A/B** (`eval_retrieval.py` + перекалибровка `RELEVANCE_SOFT`), естественный момент — реиндекс.
  - **Связано:** RAG-Стадия 5 (эволюция эмбеддера) выше; Инфра — e5-base и «РФ LLM-по-API».
  - **Файлы:** `app/rag/embeddings.py` (обёртка e5), `app/rag/pipeline.py:34` (`RELEVANCE_SOFT`),
    `scripts/load_kb.py` (`EMBEDDING_DIM`, recreate_collection), `app/core/config.py`.

## 🗂️ Данные / База знаний (структуризация, парсинг 719, кейсы)
- **Индексировать остальные части ПП №719 (тело постановления + Правила формирования реестра).** `P1` · `✅ принято → ROADMAP 1.0.1`
  - **Зачем:** сейчас RAG покрывает ТОЛЬКО приложение с требованиями к продукции (разделы
    I–XXIX, 1368 продуктов). НЕ проиндексированы: тело постановления и действующие **«Правила
    формирования и ведения реестра российской промышленной продукции»** (внесение в реестр,

    не отвечает на процедурные вопросы («как внести в реестр», «состав сведений для реестра»,
    «процедура ГИСП», «как подать заявление») — они отсекаются out-of-scope guard или (хуже)
    цепляются к продукту. Чек-лист в `navigator.py` — generic, не заземлён на Правила.
  - **Как:** Правила — ПРОЗА, а не таблицы продуктов → отдельный путь: прозовый чанкинг (по
    пунктам/абзацам), БЕЗ `structure_kb` (он для product-таблиц), отдельный `doc_type` в payload
    (`rules` vs `product`), чтобы навигатор/промпт отличал «позиция приложения» от «процедура по
    Правилам». Источник уже в `pp719_full.txt` (стр. 22856+). ВАЖНО: старые «Правила выдачи
    заключения» (стр. 22850) НЕ индексировать — **утратили силу** (ред. 29.06.2024 N 894).
  - **Связь:** заземляет чек-лист документов; **поднято в `1.0.1` (2026-06-30)** — расширяет
    назначение сервиса с «навигатор к позиции» до «навигатор + процедура реестра».
  - **Файлы:** `scripts/load_kb.py` (читает только `structured/*.json`), `app/rag/*` (`doc_type`,
    фильтр/промпт), `knowledge_base/pp719/pp719_full.txt` (источник).
- **XXIX: многоколоночные пороги по вариантам (краны) — частичный захват.** `P2` · `💡 идея`
  - **Что:** в XXIX продукты-краны (напр. `28.22.14.126` «Башенный кран») имеют пороги «не менее
    N баллов» по нескольким вариантам × этапам (датам). `min_threshold` ловит один вариант;
    `verify_structured` честно флагует ⚠ (потеряны баллы 415/445). Аналог порогов раздела X.
  - **Как:** для точного калькулятора баллов (V2) — захватывать все варианты (как `stage_header`
    для X) либо дословный блок в `notes`. Сейчас продукт находится и шкала порогов есть — для
    навигации V1 достаточно. Файл: `scripts/structure_kb.py`.
- **68 записей с пустым `product_name`.** `P1` · `✅ СДЕЛАНО 2026-06-30`
  - **Что оказалось:** не «осиротевшие подкоды, чьё имя не прицепилось» (исходная гипотеза), а
    **исключённые из приложения позиции** — строки-коды без имени и без требований
    (III=38, VII=16, XXI=10, V=2, XXV=2). В источнике: «из 28.30.31 - Позиции исключены.» /
    «28.99.39.190 - Позиция исключена.» (поправки N 610 от 17.05.2024 и N 911 от 18.06.2025).
    Старый парсер делал из них пустой `empty_stub` → хит с пустым именем на запрос по коду.
  - **Как сделано:** `structure_kb.parse_section` отбрасывает пустые строки-коды ПОСЛЕ привязки
    компонентов (реальные продукты с пустой ячейкой имени, но требованиями ниже — напр.
    `из 29.10.52.190|||` + строки-компоненты — сохранены). Существующие JSON почищены
    детерминированно (`scripts/drop_excluded_positions.py`, без DeepSeek). Реиндекс:

## 🧰 Бэкенд / API (FastAPI, БД, инфраструктура запроса)
- **Вынести модель-сервинг в отдельный долгоживущий бэкенд (отделить от UI).** `P1` · `🔬 обдумываем`
  - **Зачем:** сейчас Streamlit-MVP вызывает `navigate()` **in-process** — модель e5 (~2 ГБ)
    грузится в RAM самого UI-процесса (`@lru_cache` в `app/rag/embeddings.py:21`). Минусы:
    модель живёт в каждом UI-инстансе; перезапуск интерфейса роняет модель; нельзя
    повесить несколько фронтов (Streamlit + Telegram) на одну загруженную модель.
  - **Как (черновик):** один backend-процесс (FastAPI, `main.py` уже есть) держит модель
    и RAG-пайплайн; UI (Streamlit/Telegram/React) ходит в него по HTTP (`POST /navigate`),
    остаётся тонким. Модель грузится один раз. На проде backend и Qdrant — отдельные сервисы.
  - **Связь:** упрощает контейнеризацию (см. раздел Инфра) и эксперименты с моделями на
    ветке `dev` (можно поднять второй backend на другом порту/коллекции, не трогая рабочий).
  - **Файлы:** `frontend/streamlit_app.py` (in-process вызов), `main.py` + `app/api/` (готовый API).
- **Логирование запросов/ответов + персистентность (БД).** `P1` · `✅ принято → ROADMAP 1.0.3`
  - **Зачем:** сейчас ничего не пишется — нет аналитики частых ошибок, нет данных для петли/дообучения,

## 🧮 Функционал / Анализ (вердикт, калькулятор баллов)
- **Примерный вердикт «российская / не российская» + калькулятор баллов.** `P1` · `💡 идея`
  - **Что:** по найденной позиции сервис не только показывает требования, но и (1) **считает
    баллы** под конкретное предприятие (анкета: какие операции выполняются / доля иностранных
    товаров / наличие прав на КД-ТД и т.п.) и сравнивает с порогом позиции; (2) выдаёт
    **предварительный вердикт** «вероятно соответствует / не хватает N баллов / не соответствует».
  - **Зачем:** сейчас сервис лишь показывает критерии, а считает и решает человек —
    это главная просьба и сильнейший рычаг полезности. В `TESTING.md` (Часть 6) «не выносит
    вердикт» прямо помечено как ограничение V1; идея снимает его.
  - **Как (черновик):** новый tool `app/tools/scorer.py` — **детерминированный** счёт
    (баллы/пороги/доли НЕ доверять LLM, чтобы не было выдумок); вход — анкета по операциям
    позиции (UI с чекбоксами на `requirement_blocks`), выход — сумма баллов, разрыв до порога,
    статус. Вердикт формулирует LLM поверх детерминированного расчёта (число — от калькулятора,
    текст — от модели). Балльный (баллы≥порог) и процентный (доля иностранных ≤ X%) типы
    требований считаются по-разному — учесть оба + смешанный.
  - **Критично — зависимость от данных:** точный счёт требует ПОЛНЫХ баллов/порогов. Сейчас
    пороги разделов X и XXIX захвачены частично ([[XXIX-многоколоночные-пороги]], методички X) —
    калькулятор для них даст неполный результат. → этот функционал блокируется доразбором
    порогов (V2-данные).
  - **Принцип:** даже с калькулятором — это **черновик-подсказка**, финальный вердикт за
    экспертом ТПП (дисклеймер обязателен). Вероятно **V2/V3** (рядом с `validator.py`/`act_gen.py`).
  - **Файлы (будущие):** `app/tools/scorer.py` (расчёт), `app/core/prompts.py` (формулировка
    вердикта), `frontend/streamlit_app.py` (анкета операций), `app/tools/navigator.py` (связка).

- **Рекомендация кода ОКПД2 (и ТН ВЭД) по описанию продукции без кода.** `P1` · `🔬 обдумываем` (запрос 2026-07-05)
  - **Что:** если пользователь ввёл продукцию БЕЗ кода ОКПД2 — сервис не только отвечает по позиции,
    но и явно **рекомендует наиболее подходящий код ОКПД2 из базы** (топ-кандидаты, «предварительно,
    подтвердите»). Расширения: (2) подсказать **код ТН ВЭД** для позиции; (3) обратный вход — пользователь
    ввёл **код ТН ВЭД** → через **переходные ключи ТН ВЭД↔ОКПД2** резолвим в ОКПД2 → поиск позиции 719.
  - **Контекст (важно — меняет объём):** движок УЖЕ находит лучшую позицию для code-less запроса
    (гибрид + реранкер), а у позиции ЕСТЬ `okpd2_codes` → п.1 на ~80% это **surфейсинг** top-кода как
    явной рекомендации + дисклеймер, НЕ новый ретрив. Ошибки концентрируются на code-less (product-level
    recall@1 raw ~0.887 → ~0.987 с реранкером) → показывать **топ-3 кандидата** + флаг `low_relevance`,
    не один. Поле `tnved_codes` в схеме есть, но **почти пустое** → под ТН ВЭД нужен источник данных.
  - **Варианты интеграции:**
    - **A (минимум, без новых данных):** явная рекомендация ОКПД2 из ретрива — правило промпта для
      code-less + поле `recommended_okpd2` в ответе (топ-1..3 + «предварительно»). ~0.5 дня, высокая ценность.
    - **B (+ ТН ВЭД по переходным ключам, двунаправленно):** загрузить официальную таблицу переходных
      ключей **ТН ВЭД ЕАЭС ↔ ОКПД2** (ЕЭК/Росстат) как детерминированный lookup. Прямо: ОКПД2 → кандидаты
      ТН ВЭД. Обратно: extractor кода ТН ВЭД (10 знаков) → resolve → ОКПД2 → существующий ОКПД2-буст-поиск.
      Зависимость: достать/нормализовать ключи (one-to-many, версии редакций). ~2–3 дня + данные.
    - **C (полный):** ТН ВЭД как first-class — populate `tnved_codes` (из 719 где есть + через ключи),
      payload-индекс, поиск по любому коду. Самый большой, вероятно избыточен сейчас.
  - **Рекомендация:** A сейчас (почти готово) → B при интеграции ключей (основной ask про ТН ВЭД) → C позже.
  - **Риски/заметки:** рекомендация = **черновик** (эксперт подтверждает), критично для юр-инструмента,
    особенно на семантическом матче. Переходные ключи: версии ТН ВЭД/ОКПД2, лицензия/формат, one-to-many.
    Проверить, не теряет ли парсер ТН ВЭД, что ЕСТЬ в источнике 719 (поле `tnved_codes` пусто).
    F1-эмбеддинг (имя+раздел+код+порог) усиливает семантику имени → на руку рекомендации.
  - **Файлы (будущие):** `app/tools/navigator.py` (`extract_okpd2` → +extractor ТН ВЭД + resolve),
    `app/rag/pipeline.py` (surface `recommended_okpd2`/ТН ВЭД в `Answer`), `app/core/prompts.py`
    (правило code-less рекомендации), `app/api/chat.py` (поля ответа), новый lookup переходных ключей + загрузчик.

## ✅ Качество / Оценка (тесты, метрики точности, приёмка)
- **Eval КАЧЕСТВА ГЕНЕРАЦИИ, а не только ретрива.** `P1` · `✅ принято → ROADMAP 1.0`
  - **Зачем:** харнес (`eval_retrieval.py`) меряет, нашёлся ли верный РАЗДЕЛ, но корректность
    финального ответа DeepSeek не под метрикой. «Не врёт ли ответ по сути, полны ли тезисы» —
    сейчас не измеряется вообще (а это самая рискованная часть пайплайна).
  - **Как:** набор «запрос → эталонные тезисы ответа» (размечает эксперт), оценка LLM-as-judge или
    экспертом; метрика на ответ (полнота тезисов, отсутствие выдумок про баллы). Связать с приёмкой ≥70%.
  - **Файлы:** новый `scripts/eval_answers.py` (рядом с `eval_retrieval.py`), golden-ответы.

- **Достоверность и качество генерации ответа (анализ движка 2026-06-30).** `P0/P1` · `✅ принято → ROADMAP 1.0.2/1.0.4`
  - **Контекст:** поиск измерен и крепок (recall@1 0.95), но слой ГЕНЕРАЦИИ тонкий: анти-галлюцинация
    держится только на промпте + `temperature=0.1`, после ответа модели НЕ проверяется ничего
    (`pipeline.py:121` — лишь `_ensure_disclaimer`), метрики на сам ответ нет. **Чистые данные ≠ верный
    ответ**: модель может исказить даже идеально проиндексированный балл. Ниже — что чинить, по приоритету.
  - **P0 — чистота контекста, который видит модель:**
    1. **Заземление ответа (faithfulness).** Извлекать числа (баллы/пороги/%) из ответа регуляркой и
       сверять с блоком контекста; неподтверждённое — подсветить/убрать. Детерминированно, без 2-й
       модели; сильнее, чем только офлайн-eval. _Файл: `app/rag/pipeline.py` (после `answer()`)._
    2. **Усечение операций релевантно запросу.** `MAX_OPS_PER_HIT=12` (`pipeline.py:21,55`) берёт ПЕРВЫЕ
       12, а не относящиеся к вопросу → у мега-продуктов (автобусы 698 оп., методичка X 393 строки)
       модель видит произвольный огрызок и уверенно отвечает по нему. Ранжировать операции по близости
       к запросу перед обрезкой + поднять лимит (DeepSeek дёшев на длинном контексте) + сказать в
       промпте, что список усечён. Дешёвый пред-вариант RAG-стадии 4 (parent/child). _Файл: `pipeline.py:format_context`._
    3. **Показать модели, какой хит точный.** `okpd2_match` считается (`retriever.py:121`), но
       `format_context` его НЕ передаёт — все 5 позиций равны, перепредставленный раздел X тянет мусор,
       модель смешивает требования разных продуктов. Помечать `[1] (точное совпадение по ОКПД2)` +
       обрезать слабый хвост хитов по обрыву score (часто релевантен top-1, а в контекст идёт 5).
       _Файлы: `pipeline.py:format_context`, `retriever.py:search`._
    4. **Порог релевантности для кейсов.** `search_cases` (`retriever.py:174`) инжектит top-3 как
       «высший приоритет» независимо от score → слабо связанный кейс активно вредит (правило 1а просит
       модель саму отфильтровать — ненадёжно). Ввести порог score перед инъекцией, иначе не помечать
       «высший приоритет». _Файлы: `retriever.py:search_cases`, `pipeline.py`._
  - **P1 — промпт (`NAVIGATOR_SYSTEM_PROMPT`, `prompts.py:103`):**
    - **Цитаты:** обязать инлайн-ссылки `[1]/[2]` на конкретную позицию + валидировать (сейчас правило 3
      просит назвать позицию, но привязки claim→источник нет → в мульти-хит ответах путается, чьё требование).
    - **Аудитория:** `«предприятия и эксперты ТПП»` (`prompts.py:106`) → под эксперт-first (плотнее,
      агрессивнее цитировать `source_anchor`).
    - **Язык/CJK:** усилить «только русский» + пост-зачистка CJK-диапазона — это та же проблема, что
      запись «Протечка иероглифов…» в разделе LLM (лечится в промпте + постпроцессинге).
    - **Few-shot:** 1–2 примера (вкл. «не найдено» и «вне сферы 719») стабилизируют формат а/б/в;
      системный промпт кешируется DeepSeek → почти бесплатно.
    - **Out-of-scope:** любой код, даже `«29»`, гасит guard (`pipeline.py:100`: `not any okpd2_match`) —
      не гасить флаг на слабом иерархическом совпадении кода.
  - **P2 — робастность и измеримость:** timeout/retry на DeepSeek (`pipeline.py:113`, рваная сеть);
    `max_tokens`/seed (репроизводимость eval); нормализовать `_ensure_disclaimer` (`pipeline.py:84` —
    перефраз пометки даёт ДВЕ); логирование вход/выход (см. логирование/БД, ROADMAP 1.0.3) — без него
    не разобрать плохой ответ и не собрать golden-ответы из трафика.
  - **Порядок:** (1) чистый контекст P0.2–P0.4 → (2) промпт P1 → (3) пост-проверка чисел P0.1 +
    дисклеймер + timeout → (4) `eval_answers.py` (зафиксировать число и двигать его). P0/P1 → ROADMAP 1.0.2,
    измеримость → 1.0.4.

- **Бенчмарк «наш движок vs вендорский managed-RAG» (build-vs-buy, эмпирически).** `P2` · `🧪 ГИПОТЕЗА — вернуться ПОСЛЕ демо`
  - **Зачем:** решение «managed-RAG РФ (Cloud.ru Evolution Managed RAG / Yandex AI Studio / MWS) не берём»

  - **Как:** поднять вендорский RAG на ТОМ ЖЕ корпусе (приложение 719) → прогнать ТЕ ЖЕ golden-запросы
    (46 + negative/confusable) через их ассистент-API → оценить ТЕМИ ЖЕ нашими evaluators (faithfulness
