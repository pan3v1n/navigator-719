## 🔎 RAG (поиск, ретрив, эмбеддинги, Qdrant)
- **Out-of-scope guard: отсекать запросы вне сферы 719.** `P1` · `🔬 обдумываем`
  - **Зачем:** на продукции вне 719 (напр. «хлебобулочные изделия») поиск без порога
    релевантности возвращает «ближайший мусор» (наблюдали выдачу «Микрофоны,
    громкоговорители…»). Сейчас заглушка «не найдено» срабатывает только при полностью
    пустом списке, а Qdrant на непустой коллекции всегда что-то отдаёт.
  - **Как (черновик, по возрастанию надёжности):**
    1. Порог по dense-сходству top-1 (косинус e5), а **не** по RRF-score (RRF —
       `1/(k+rank)`, несравним между запросами). Ниже порога → «вне сферы 719/уточните».
    2. Инструкция в `NAVIGATOR_SYSTEM_PROMPT`: если контекст не соответствует продукции —
       прямо сказать «позиция не найдена», не выдумывать.
    3. Комбинация 1+2 (рекомендуется) + быстрый тест на нерелевантный запрос.
  - **Файлы:** `app/rag/retriever.py:112` (search), `app/rag/pipeline.py:85` (ветка «не
    найдено»), `app/core/prompts.py`.

## 🧰 Бэкенд / API (FastAPI, БД, инфраструктура запроса)
- **Вынести модель-сервинг в отдельный долгоживущий бэкенд (отделить от UI).** `P1` · `🔬 обдумываем`
  - **Зачем:** сейчас Streamlit-MVP вызывает `navigate()` **in-process** — модель e5 (~2 ГБ)
    грузится в RAM самого UI-процесса (`@lru_cache` в `app/rag/embeddings.py:21`). Минусы:
    модель живёт в каждом UI-инстансе; перезапуск интерфейса роняет модель; нельзя
    повесить несколько фронтов (Streamlit + Telegram) на одну загруженную модель.
  - **Как (черновик):** один backend-процесс (FastAPI, `main.py` уже есть) держит модель
    и RAG-пайплайн; UI (Streamlit/Telegram/React) ходит в него по HTTP (`POST /navigate`),
    остаётся тонким. Модель грузится один раз. На проде backend и Qdrant — отдельные сервисы.
  - **Связь:** упрощает контейнеризацию (см. раздел Инфра) и эксперименты с моделями на
    ветке `dev` (можно поднять второй backend на другом порту/коллекции, не трогая рабочий).
  - **Файлы:** `frontend/streamlit_app.py` (in-process вызов), `main.py` + `app/api/` (готовый API).

## ⚙️ Инфраструктура / DevOps (Docker, хостинг, деплой, мониторинг)
- **Надёжный provisioning модели e5 (offline / зеркало / ручная папка).** `P1` · `🔬 обдумываем`
  - **Зачем:** скачка весов e5 (~2.1 ГБ) с CDN HuggingFace из РФ рвётся (DPI/`zapret` →
    `IncompleteRead`, `408 Timeout`). Свежий клон спотыкается на первом запуске. Решение
    «модель лежит локально + путь в `.env`» сидит только на конкретном ПК (`.env`, `models/`,
    `HF_HOME` — всё в gitignore), в репозиторий не попадает → разрыв «работает у меня».
  - **Как (что уже частично сделано):** `hf_xet` в `requirements.txt` (чанковая докачка);
    в `.env.example` — варианты «локальный путь» и `HF_ENDPOINT=https://hf-mirror.com`.
    **Осталось:** раздел в `docs/SETUP.md` «3 способа добыть e5» (автоскачка / зеркало /
    ручная папка) + опционально скрипт-провижнинг. Особенно важно перед веткой `dev` и
    git worktree (в каждом окружении модель нужна заново).
  - **Связь:** [[вынести-модель-в-отдельный-сервис]] (один backend держит модель — провижнить
    её надо в одном месте, а не в каждом UI-инстансе).
