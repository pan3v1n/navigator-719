## Как пользоваться
- Кидай идею в нужный раздел. Не бойся дублей и «сырых» формулировок — лучше записать.
- Формат записи (по возможности):
  - **Что** — суть идеи в одну строку.
  - **Зачем** — какую боль решает / что улучшает.
  - **Как** — набросок реализации (если есть). Необязательно.
  - метки: приоритет `P0/P1/P2`, статус, область.
- Статусы: `💡 идея` · `🔬 обдумываем` · `✅ принято → ROADMAP` · `❌ отклонено` · `🧊 заморожено`
- Приоритет: `P0` критично · `P1` важно · `P2` приятно иметь.

## 🔎 RAG (поиск, ретрив, эмбеддинги, Qdrant)
- **Out-of-scope guard: отсекать запросы вне сферы 719.** `P1` · `🔬 обдумываем`
  - **Зачем:** на продукции вне 719 (напр. «хлебобулочные изделия») поиск без порога
    релевантности возвращает «ближайший мусор» (наблюдали выдачу «Микрофоны,
    громкоговорители…»). Сейчас заглушка «не найдено» срабатывает только при полностью
    пустом списке, а Qdrant на непустой коллекции всегда что-то отдаёт.
  - **Как (черновик, по возрастанию надёжности):**
    1. Порог по dense-сходству top-1 (косинус e5), а **не** по RRF-score (RRF —
       `1/(k+rank)`, несравним между запросами). Ниже порога → «вне сферы 719/уточните».
    2. Инструкция в `NAVIGATOR_SYSTEM_PROMPT`: если контекст не соответствует продукции —
       прямо сказать «позиция не найдена», не выдумывать.
    3. Комбинация 1+2 (рекомендуется) + быстрый тест на нерелевантный запрос.
  - **Файлы:** `app/rag/retriever.py:112` (search), `app/rag/pipeline.py:85` (ветка «не
    найдено»), `app/core/prompts.py`.

- ### 📈 План улучшения RAG по стадиям (0–5) `🔬 обдумываем`
  > Порядок = приоритет. Принцип: **сначала измеримость, потом точность, потом масштаб.**
  > Обоснование текущей архитектуры и подробный разбор — в [RAG_EXPLAINED.md](RAG_EXPLAINED.md).
  > Каждое улучшение проверяем числом на харнесе из стадии 0, а не «на глаз».

  - **Стадия 0 — Eval-харнес (метрика качества ретрива).** `P0` · предусловие всего ⚠️ делать ПЕРВЫМ
    - **Что такое eval-харнес:** автоматический «экзамен» для поиска. Это (1) **golden set** —
      список пар «запрос → правильная позиция/раздел 719» (эталон, размечает человек/эксперт);
      (2) **прогонщик** — скрипт, который гоняет каждый запрос через `retriever.search` и
      сравнивает выдачу с эталоном; (3) **метрики** — числа, отражающие качество:
      - **recall@k** — доля запросов, где правильная позиция попала в топ-k (нашли ли вообще);
      - **MRR** (Mean Reciprocal Rank) — насколько высоко стоит правильный ответ (1.0 = всегда
        первый; 0.5 = в среднем второй) — отражает качество ранжирования;
      - **hit-rate / precision@k** — точность верхушки выдачи.
    - **Зачем:** сейчас есть только smoke-тесты (4 запроса «на глаз»). Любая правка ниже (порог,
      реранкер, веса RRF) без метрики = **гадание**. Харнес даёт «точку отсчёта» и позволяет
      сказать «правка X подняла recall@5 с 0.78 до 0.91» вместо «вроде стало лучше».
    - **Как:** превратить `docs/test_cases.*` (12 кейсов) в стартовый golden set, расширить до
      ~30–50 (29 разделов + out-of-scope), скрипт `scripts/eval_retrieval.py` → таблица метрик.
      _Сделано 2026-06-18: `scripts/eval_golden.json` (46 кейсов) + `scripts/eval_retrieval.py`._
    - **Цена/риск:** низкая, чистый код, без новых зависимостей. **Максимальный рычаг.**

  - **Стадия 1 — Out-of-scope guard.** `P1` — см. отдельную запись выше (порог dense top-1 +
    инструкция в промпте). Калибруется на харнесе из стадии 0. Самый быстрый честный выигрыш.

  - **Стадия 2 — Реранкер (cross-encoder).** `P1` · `🔬`
    - **Что:** после гибрида (top-20) добавить переранжирование cross-encoder'ом (смотрит пару
      «запрос+кандидат» целиком, точнее bi-encoder) → топ-5 берём из переранжированного.
    - **Качество:** заметный прирост precision@k, когда верный ответ в top-20, но не в top-5.
    - **Риск/условия:** ещё одна модель в RAM + скачивание (RF/DPI). Брать малый мультиязычный
      реранкер (BGE-reranker-base / jina-multilingual), провижнить как e5 (локальная папка).
      Замерить выигрыш на харнесе — если мал, не тащить.

  - **Стадия 3 — Тюнинг гибрида + обработка запроса.** `P2` · `🔬`
    - RRF `k`, prefetch-limit, баланс dense/sparse — подобрать на golden set.
    - **Query expansion** (разговорное→регламентное, словарь синонимов) или **HyDE** (LLM генерит
      гипотетическое описание по короткому запросу → эмбеддим его) — лечит короткие запросы.

  - **Стадия 4 — Гранулярность parent/child (ближе к V2).** `P2` · `🔬`
    - **Проблема:** мега-продукты усекаются до 12 операций в контексте (`MAX_OPS_PER_HIT`).
    - **Что:** индексировать на уровне блоков операций (child), в контекст подтягивать
      родительский продукт (small-to-big / auto-merging). Точка решения «вернуть LlamaIndex
      (готовые parent-retrievers) или дописать руками».

  - **Стадия 5 — Эволюция эмбеддера (по мере роста).** `P2` · `🔬`
    - **BGE-m3** — одна модель: dense + sparse + ColBERT-мультивектор (Qdrant поддерживает
      late interaction) → выше precision ценой хранилища; может заменить e5 + ручной BM25.
    - **Дообучение/адаптация e5** на подтверждённых кейсах эксперта (петля уже готова), когда
      кейсов накопится достаточно.

  - **Сводка приоритетов:** 0 (харнес, сейчас) → 1 (guard) → 2 (реранкер) / 3 (тюнинг) → 4 (V2) → 5 (потолок).
  - **Связанное:** расхождение доки↔код — в `CLAUDE.md` стек заявляет **LlamaIndex**, но RAG
    рукописный (qdrant_client + sentence_transformers напрямую). Привести стек-таблицу в
    соответствие ИЛИ осознанно вернуть LlamaIndex на стадии 4.

## 🗂️ Данные / База знаний (структуризация, парсинг 719, кейсы)
- **Индексировать остальные части ПП №719 (тело постановления + Правила формирования реестра).** `P1` · `🔬 обдумываем`
  - **Зачем:** сейчас RAG покрывает ТОЛЬКО приложение с требованиями к продукции (разделы
    I–XXIX, 1672 продукта). НЕ проиндексированы: тело постановления и действующие **«Правила
    формирования и ведения реестра российской промышленной продукции»** (внесение в реестр,

    не отвечает на процедурные вопросы («как внести в реестр», «состав сведений для реестра»,
    «процедура ГИСП», «как подать заявление») — они отсекаются out-of-scope guard или (хуже)
    цепляются к продукту. Чек-лист в `navigator.py` — generic, не заземлён на Правила.
  - **Как:** Правила — ПРОЗА, а не таблицы продуктов → отдельный путь: прозовый чанкинг (по
    пунктам/абзацам), БЕЗ `structure_kb` (он для product-таблиц), отдельный `doc_type` в payload
    (`rules` vs `product`), чтобы навигатор/промпт отличал «позиция приложения» от «процедура по
    Правилам». Источник уже в `pp719_full.txt` (стр. 22856+). ВАЖНО: старые «Правила выдачи
    заключения» (стр. 22850) НЕ индексировать — **утратили силу** (ред. 29.06.2024 N 894).
  - **Связь:** заземляет чек-лист документов; вероятно V2 (расширяет назначение сервиса с
    «навигатор к позиции» до «навигатор + процедура реестра»).
  - **Файлы:** `scripts/load_kb.py` (читает только `structured/*.json`), `app/rag/*` (`doc_type`,
    фильтр/промпт), `knowledge_base/pp719/pp719_full.txt` (источник).
- **XXIX: многоколоночные пороги по вариантам (краны) — частичный захват.** `P2` · `💡 идея`

## 🧰 Бэкенд / API (FastAPI, БД, инфраструктура запроса)
- **Вынести модель-сервинг в отдельный долгоживущий бэкенд (отделить от UI).** `P1` · `🔬 обдумываем`
  - **Зачем:** сейчас Streamlit-MVP вызывает `navigate()` **in-process** — модель e5 (~2 ГБ)
    грузится в RAM самого UI-процесса (`@lru_cache` в `app/rag/embeddings.py:21`). Минусы:
    модель живёт в каждом UI-инстансе; перезапуск интерфейса роняет модель; нельзя
    повесить несколько фронтов (Streamlit + Telegram) на одну загруженную модель.
  - **Как (черновик):** один backend-процесс (FastAPI, `main.py` уже есть) держит модель
    и RAG-пайплайн; UI (Streamlit/Telegram/React) ходит в него по HTTP (`POST /navigate`),
    остаётся тонким. Модель грузится один раз. На проде backend и Qdrant — отдельные сервисы.
  - **Связь:** упрощает контейнеризацию (см. раздел Инфра) и эксперименты с моделями на
    ветке `dev` (можно поднять второй backend на другом порту/коллекции, не трогая рабочий).
  - **Файлы:** `frontend/streamlit_app.py` (in-process вызов), `main.py` + `app/api/` (готовый API).

## ⚙️ Инфраструктура / DevOps (Docker, хостинг, деплой, мониторинг)
- **Надёжный provisioning модели e5 (offline / зеркало / ручная папка).** `P1` · `🔬 обдумываем`
  - **Зачем:** скачка весов e5 (~2.1 ГБ) с CDN HuggingFace из РФ рвётся (DPI/`zapret` →
    `IncompleteRead`, `408 Timeout`). Свежий клон спотыкается на первом запуске. Решение
    «модель лежит локально + путь в `.env`» сидит только на конкретном ПК (`.env`, `models/`,
    `HF_HOME` — всё в gitignore), в репозиторий не попадает → разрыв «работает у меня».
  - **Как (что уже частично сделано):** `hf_xet` в `requirements.txt` (чанковая докачка);
    в `.env.example` — варианты «локальный путь» и `HF_ENDPOINT=https://hf-mirror.com`.
    **Осталось:** раздел в `docs/SETUP.md` «3 способа добыть e5» (автоскачка / зеркало /
    ручная папка) + опционально скрипт-провижнинг. Особенно важно перед веткой `dev` и
    git worktree (в каждом окружении модель нужна заново).
  - **Связь:** [[вынести-модель-в-отдельный-сервис]] (один backend держит модель — провижнить
    её надо в одном месте, а не в каждом UI-инстансе).
