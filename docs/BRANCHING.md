# Ветки и рабочий процесс — Навигатор ПП №719

Модель ветвления проекта и как с ней работать. Цель — отделить **стабильную версию,
которую тестирует эксперт ТПП**, от экспериментов с моделями/интерфейсом/функционалом.

---

## Модель веток

```
main ───●──────────●────────────●         стабильная: «то, что тестирует эксперт»
         \        / \          /            теги на приёмках: v1.0, v1.1, …
          dev ───●───●────●───●──           интеграция: работает, копится к релизу
                  \      /
                   exp/* ●──●               рискованные спайки; большинство выбрасываем
```

| Ветка | Что это | Правила |
|---|---|---|
| **`main`** | Эталон. Разворачивается и проверяется экспертом. | Никаких прямых экспериментов. Только merge из `dev` (или `hotfix`) **через PR**. Каждый релиз → тег `vX.Y`. Всегда запускается. |
| **`dev`** | Интеграция. Готовое, но ещё не принятое. **Рабочая ветка по умолчанию.** | Сюда вливаются удачные эксперименты. Должна оставаться запускаемой. |
| **`exp/<тема>`** | Короткоживущие спайки от `dev`: новая LLM, RAG-переделка, React вместо Streamlit. | Удачно → merge в `dev`. Неудачно → `git branch -D` без сожалений. **В origin не пушатся** (см. хук). |

---

## Жизненный цикл изменения

1. Идея из [IDEAS.md](IDEAS.md) → ветка `exp/<тема>` от `dev`.
2. Пробуешь. Не взлетело → `git branch -D exp/...` (в IDEAS пометить ❌).
3. Взлетело → merge в `dev`, прогнать `tests/` + смоук-кейсы (`scripts/run_test_cases.py`).
4. `dev` стабилизирован → **PR `dev → main`** → `/code-review` → merge → **тег** `vX.Y` → бамп `APP_VERSION`.
5. Эксперт тестирует строго `main` (стабильный тег).

## PR dev → main

```powershell
git switch dev && git push origin dev          # убедиться, что dev в origin
gh pr create --base main --head dev --title "..." --body "..."
# после ревью:
gh pr merge --merge        # или --squash
git switch main && git pull
git tag vX.Y && git push origin vX.Y           # тег на приёмке
```
`exp/* → dev` — прямым merge, без PR.

## Эксперименты через git worktree (рекомендованный способ)

Worktree = отдельная папка с другой веткой, **общий `.git`**. Рабочий `main`/`dev` не трогается,
у эксперимента **свой `.env`** (своя Qdrant-коллекция, свой порт) — можно крутить два сервиса разом.

```powershell
# из корня репозитория создать эксперимент в соседней папке
git worktree add ../nav-exp-bge -b exp/bge-embeddings dev

cd ../nav-exp-bge
copy ..\navigator-719\.env .env        # затем поправить под эксперимент (см. ниже)
.venv... # своё окружение/зависимости при необходимости

# закончили:
cd ..\navigator-719
git worktree remove ../nav-exp-bge     # если ветка не нужна — потом git branch -D exp/bge-embeddings
```

> `.env`, `models/`, `qdrant_storage/`, `.venv/` — в `.gitignore`, у каждого worktree свои.

## Изоляция данных Qdrant по веткам ⚠️

`load_kb.py` с другой моделью/схемой **затирает коллекцию `pp719`**, на которой стоит приёмка
эксперта. Поэтому в эксперименте задавай своё имя коллекции в `.env`:

```env
# в worktree эксперимента
QDRANT_COLLECTION=pp719_exp_bge      # рабочая pp719 остаётся нетронутой
EMBEDDING_MODEL=...                  # своя модель эксперимента
APP_PORT=8001                        # если поднимаешь API рядом с рабочим
```
Streamlit рядом с рабочим — на другом порту: `streamlit run ... --server.port 8502`.

## Поведение автопуш-хука

`post-commit` (локальный, не в гите — ставится на каждом ПК):
- **`main`/`dev` и прочие** → `git push origin HEAD` (пуш текущей ветки в одноимённую удалённую).
- **`exp/*`** → пуш пропускается (эксперименты не летят в origin).
- `detached HEAD` → пуш пропускается.
- Ниже в хуке — блок graphify (пересборка графа кода). **При переустановке хука не затирай его.**

Канонический верх хука (push-часть):
```sh
#!/bin/sh
_BRANCH=$(git rev-parse --abbrev-ref HEAD 2>/dev/null)
case "$_BRANCH" in
  exp/*) echo "[hook] $_BRANCH — эксперимент, автопуш пропущен" ;;
  HEAD)  echo "[hook] detached HEAD — автопуш пропущен" ;;
  *)     git push origin HEAD ;;
esac
# ниже — блок graphify (graphify hook install), не удалять
```

## Ежедневно

```powershell
git switch dev && git pull        # начало работы — на dev
# ... работа, коммиты (автопуш сам отправит dev) ...
```
Готово к релизу → PR `dev → main` (см. выше). Стабильную версию для эксперта берём из `main`/тега.
