## Рекомендация

1. **Основной вход — 6-значный одноразовый код на email (OTP), а не magic link.** Код живёт 10 минут, на один код даётся не больше 5 попыток. В БД хранится только HMAC кода, вызов привязан к сессии браузера. Ответ на запрос кода одинаковый для существующих и несуществующих адресов. Ссылку в письме (magic link) почтовые сканеры корпоративной почты «нажимают» за пользователя и тем самым расходуют её, а код от этого не страдает ([Supabase](https://supabase.com/docs/guides/troubleshooting/otp-verification-failures-token-has-expired-or-otp_expired-errors-5ee4d0.md)). Так совпадаем с макетом владельца и лучше всего ложимся на сценарий «гость → регистрация».
2. **Отправка писем — Yandex Cloud Postbox по SMTP с того же облачного аккаунта, где стоит VM.** Первые 2 000 писем в месяц бесплатны ([тарифы Postbox](https://yandex.cloud/ru/docs/postbox/pricing)), а наш объём заведомо меньше. Отправитель — ASCII-адрес на корневом домене в punycode, например `noreply@xn--719--83dani8b8bqyy.xn--p1ai`. SMTPUTF8 при этом не нужен (RFC 6531/8616, см. §2.2). DNS: DKIM (2 CNAME), SPF `include:spf.postbox.yandexcloud.net`, DMARC `p=none` для начала. Запасной провайдер — Unisender Go.
3. **Яндекс ID — вторая кнопка, второй этап, только для привязки к уже существующей учётке.** Новые учётки по нему не создавать и не сопоставлять автоматически по `default_email`: Яндекс сам пишет, что не проверяет достоверность данных Яндекс ID (п. 4.5 [Условий API](https://yandex.ru/legal/authid_api/)). С правовой стороны Яндекс ID — самый «чистый» из дешёвых вариантов (см. §4), но делать его единственным способом входа нельзя: у части сотрудников палат может не быть аккаунта, а личный аккаунт не отключается, когда сотрудник уходит из палаты.
4. **Правовой риск реален, и сегодняшний вход по паролю в той же «серой зоне», что и код на почту.** С 07.07.2026 действует ст. 13.55 КоАП: штраф для юрлица 500–700 тыс. ₽, дела рассматривает Роскомнадзор (ст. 23.44 КоАП) **[ПЕРВОИСТОЧНИК]**. По буквальному тексту ч. 10 ст. 8 149-ФЗ исключения для закрытого B2B-сервиса нет. Код на почту допустим, только если собственную систему входа признать «иной информационной системой» российского владельца по п. 4. По пересказу юрфирмы BIRCH, эксперты РКН на Дне открытых дверей 14.08.2026 это допустили **[ВТОРИЧНЫЙ]**. Официального письменного разъяснения Минцифры/РКН я не нашёл **[НЕ ПРОВЕРЕНО]**. Поэтому до запуска нужно: (а) установить, кто юридический владелец сайта; (б) получить короткое заключение юриста; (в) держать Яндекс ID (или телефон) как «безусловно допустимый» способ входа.
5. **Переход — без большого переключения в один день.** Добавить отдельное подтверждённое и уникальное поле «email для входа». Это не то же самое, что редактируемый «рабочий email» кабинета, который добавил кабинет (ветка `feat/auth-account`): на нём вход строить нельзя, см. §6.1. Вход по паролю остаётся второстепенной ссылкой на переходный период. Администраторам — пароль плюс код (второй фактор). Пароль для роли `user` отключается после того, как все учётки получат подтверждённый email.
6. **152-ФЗ:** нужно обновить отдельный документ согласия (с 01.09.2025 согласие оформляется отдельно от иных документов) и политику — добавить email для входа, идентификатор Яндекса, обработчика-рассыльщика по поручению. Обновить уведомление в РКН до 15-го числа следующего месяца. Сначала выяснить, подано ли уведомление вообще (§4.7).

## 0. Отправная точка: что в коде сейчас

- Вход: `POST /login` (`app/api/web.py`, `login_submit`) — логин и пароль, bcrypt (`app/api/auth.py`, `authenticate`). Лимит 10 попыток в минуту с IP (`SlidingWindow` в памяти, `app/api/ratelimit.py`). Сообщение об ошибке одинаковое: «Неверный логин или пароль».
- Сессия — подписанная кука Starlette (`main.py`: `same_site="lax"`, `https_only=COOKIE_SECURE`, `max_age=None`). Документация Starlette: данные сессии «readable but not modifiable» ([starlette.dev](https://starlette.dev/middleware/)), то есть **класть код в сессию нельзя**, можно только идентификатор вызова.
- «Запомнить меня» — кука `remember719`, подписанный itsdangerous `user_id` на 30 дней (`auth.py`). Отозвать её на сервере нельзя: в токене нет ни номера версии, ни эпохи.
- Учётки выдаёт `scripts/seed_users.py` (логины `<регион>.expert1`, пароли около 8 символов). Профиль роли `user` — обязательный гейт (`needs_profile`): ФИО, регион, Telegram, согласие.
- CSRF-токенов в формах нет. POST-формы защищены тем, что SameSite=Lax не отправляет куку на межсайтовый POST ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)).
- Миграции — `app/db/engine.py::_ensure_columns`: `ALTER TABLE … ADD COLUMN` для SQLite.
- ⚠ **Кабинет (ветка `feat/auth-account`, коммит `68df2c4`):** в `User` добавлены `position`, `email`, `phone`, `org`, `inn`. `email` — необязательный «рабочий email», пользователь меняет его в кабинете **без проверки** и без уникальности (`app/db/models.py`, `app/db/queries.py::update_profile`, `app/api/web.py::profile_submit`). На этом поле вход строить нельзя, см. §6.1.

## 1. Вход по одноразовому коду на email (OTP) и magic link

### 1.1 Поток (рекомендуемый)

1. `GET /login` → поле «Рабочий email», галочка «Запомнить меня», кнопка «Получить код».
2. `POST /login/code` → нормализуем адрес и проверяем лимиты (по IP и по адресу). Создаём вызов (challenge), его `id` кладём в сессию. Письмо уходит **в фоне** (FastAPI `BackgroundTasks`), чтобы время ответа не выдавало, есть ли такая учётка. Затем `303 → GET /login/code`.
3. `GET /login/code` → «Мы отправили код на n***@tpp.ru, если адрес зарегистрирован», поле кода (`inputmode="numeric" autocomplete="one-time-code"`), «Отправить ещё раз» (не чаще раза в 60 с).
4. `POST /login/code/verify` → сверяем код с вызовом из **этой** сессии, учитываем попытки, срок, одноразовость, сравниваем через `hmac.compare_digest`. При успехе: очистить сессию → `login_session` → (по галочке) `set_remember_cookie` → `/`. Дальше работает существующий гейт профиля.

### 1.2 Параметры и обоснование

| Параметр | Значение | Основание |
|---|---|---|
| Длина кода | 6 цифр, `secrets.randbelow(10**6)` | NIST SP 800-63B-4: «at least six decimal digits» для out-of-band секретов, §3.1.3.2 [ПЕРВОИСТОЧНИК] ([NIST](https://pages.nist.gov/800-63-4/sp800-63b.html)) |
| Срок жизни | 10 мин; при задержках доставки на пилоте — до 15 | NIST: «invalid unless completed within 10 minutes», §3.1.3.2 [ПЕРВОИСТОЧНИК]. Грейлистинг может задерживать первое письмо: в RFC 6647 пример — 30 мин, допустимый диапазон 1 мин – 24 ч [ПЕРВОИСТОЧНИК] ([RFC 6647](https://www.rfc-editor.org/rfc/rfc6647.html)) |
| Попыток на один код | 5, потом вызов сгорает | NIST требует верхнюю границу 100 подряд, ниже — можно (§3.2.2) [ПЕРВОИСТОЧНИК]; 5 — моя рабочая точка [ВЫВОД] |
| Новых кодов на адрес | не чаще 1 раза в 60 с, не больше 5 в час и 20 в сутки | OWASP: «rate-limiting on a per-account basis», защита от засыпания ящика письмами [ПЕРВОИСТОЧНИК] ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)) |
| Запросов кода с IP | 10 в час (существующий `SlidingWindow`) | там же |
| Одноразовость | `consumed_at` ставится при успехе; новый код гасит прежние | OWASP: «Single use and expire», «Invalidated after they have been used» [ПЕРВОИСТОЧНИК] |

**Перебор [ВЫВОД, арифметика]:** при 10⁶ вариантов, 5 попытках на код и не больше 5 кодов в час на адрес шанс угадать за час ≤ 25/10⁶ = 0,0025 %. При потолке 20 кодов в сутки — ≤ 100/10⁶ = 0,01 % за сутки. Лимит по адресу должен лежать **в БД** (счёт вызовов за окно), а не только в памяти: перезапуск процесса обнуляет `SlidingWindow`.

**Важная оговорка про силу способа [ПЕРВОИСТОЧНИК]:** NIST 800-63B-4 (стандарт США, для нас не обязателен) прямо пишет «Email SHALL NOT be used for out-of-band authentication» (§3.1.3.1). Код на почту ровно настолько надёжен, насколько защищён почтовый ящик. Для `user`/`expert` это приемлемо [ВЫВОД]. Для `admin` нужен второй фактор (пароль плюс код или Яндекс ID).

### 1.3 Перечисление учёток

- Ответ на `POST /login/code` один и тот же — по статусу, телу, редиректу и времени — для известного и неизвестного адреса. Отсюда и отправка в фоне. OWASP: «Return a consistent message», «responses return in a consistent amount of time» [ПЕРВОИСТОЧНИК].
- Что получает **неизвестный** адрес — решение владельца (§7):
  - (а) ничего: строже, но человек ждёт код, который не придёт;
  - (б) письмо «учётной записи с этим адресом нет — оставьте заявку <ссылка на лендинг>»: перечисления на сайте нет, человеку понятно, что делать.
  
  С учётом будущего «гость → регистрация» удобнее (б) [ВЫВОД].
- Ссылки в письмах строить **из настройки** (`PUBLIC_DOMAIN` + `APP_SUBDOMAIN`), а не из заголовка `Host`. OWASP: «Don't rely on the Host header» [ПЕРВОИСТОЧНИК].

### 1.4 CSRF и фиксация сессии

- Вызов кода привязан к сессии браузера: кука `SameSite=Lax` не уходит на межсайтовый POST ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)) [ПЕРВОИСТОЧНИК]. Поэтому подделанная форма `POST /login/code/verify` с чужого сайта не найдёт вызов, и «login CSRF» (подсунуть жертве свою сессию) отпадает [ВЫВОД].
- `POST /login/code` (запрос кода) кука не защищает. Вред от его подделки — письма жертве, и это гасят лимиты из §1.2. Дополнительно можно проверять заголовок `Origin`/`Referer` на всех POST формы входа [ВЫВОД].
- При успешном входе — `request.session.clear()`, потом `user_id`, чтобы не переносить данные из сессии до входа [ВЫВОД].

### 1.5 Magic link — почему не основным способом

- Шлюзы безопасности корпоративной почты сами открывают ссылки из писем и **тратят одноразовый токен**. Supabase называет это частой причиной ошибок «expired» и советует код вместо ссылки или страницу подтверждения [ПЕРВОИСТОЧНИК] ([Supabase](https://supabase.com/docs/guides/troubleshooting/otp-verification-failures-token-has-expired-or-otp_expired-errors-5ee4d0.md)). Пользователи у нас — сотрудники палат с корпоративной почтой, это как раз наш случай.
- Ссылка открывается в браузере почтового клиента, часто на другом устройстве, а «Запомнить меня» и сессия нужны в браузере, где идёт работа [ВЫВОД].
- Если ссылку всё же добавлять, то только как GET на страницу с кнопкой, а токен тратить на POST по кнопке ([обзор практики](https://laravel-news.com/package/pushery-email-magic-link-for-laravel)) [ВТОРИЧНЫЙ].

### 1.6 Привязка существующих учёток (username → email)

- На 07.10.2026 на бою 28 пользователей (`CLAUDE.md`, запись выкатки `test27`). Таблица «логин → человек» ведётся офлайн (`scripts/seed_users.py`, докстринг).
- Варианты:
  - (а) admin вносит email для входа в `/admin` или скриптом (`seed_users.py --login-email`). Адрес считается подтверждённым после первого успешного входа по коду;
  - (б) пользователь, вошедший по паролю, в кабинете «Способы входа» указывает email, получает на него код и подтверждает;
  - (в) из одобренной заявки лендинга (`leads.email`) создаётся учётка с этим адресом, и уходит письмо-приглашение.
- Уникальность — уникальным индексом по нормализованному адресу. SQLite не умеет `ADD COLUMN … UNIQUE` ([sqlite.org](https://www.sqlite.org/lang_altertable.html)) [ПЕРВОИСТОЧНИК], поэтому колонка добавляется через `_ensure_columns`, а индекс — отдельно: `CREATE UNIQUE INDEX IF NOT EXISTS`.
- Нормализация: `strip`, нижний регистр; домен с кириллицей (бывают ящики на `.рф`) перевести в A-label (IDNA) и для хранения, и для отправки [ВЫВОД].

### 1.7 Что хранить в БД

- `users`:
  - `login_email` (VARCHAR 255, NULL, уникальный индекс);
  - `login_email_verified_at`;
  - `auth_epoch INTEGER DEFAULT 0` — чтобы отзывать «запомнить меня»;
  - `password_login_disabled BOOLEAN DEFAULT 0` — флаг на переходный период.
- Новая таблица `login_codes`:
  - `id` (случайный, 128 бит), `email_norm`, `user_id NULL`, `purpose` (`login` | `bind_email` | `signup`);
  - `code_hmac` — HMAC-SHA256 от отдельного секрета, а не голый хеш: 10⁶ вариантов перебираются офлайн мгновенно [ВЫВОД];
  - `created_at`, `expires_at`, `attempts`, `consumed_at`.
  - **IP не хранить** — как в заявках (`app/api/leads.py`, `Lead`). Строки старше суток удалять, по аналогии с `purge_old_leads`.
- Второй этап — `user_identities` (`user_id`, `provider='yandex'`, `subject` = Yandex `id` или `psuid`, `linked_at`). Сам OAuth-токен **не хранить**: он нужен один раз, чтобы получить `/info` [ВЫВОД].

### 2.2 Отправитель на кириллическом (IDN) домене

- **SMTPUTF8 не нужен, если адрес полностью ASCII: латинская локальная часть и домен в punycode (A-label).** RFC 6531: A-label-домен «is not considered to be "internationalized"». Расширение нужно, только когда в конверте есть не-ASCII адрес [ПЕРВОИСТОЧНИК] ([RFC 6531](https://www.rfc-editor.org/rfc/rfc6531.html)).
- **SPF/DKIM/DMARC для IDN** — RFC 8616: записи DNS остаются ASCII («Strings stored in DNS records remain ASCII»). U-labels перед проверкой SPF/DMARC переводятся в A-labels. В DKIM `d=` для обычной (не EAI) почты — A-labels [ПЕРВОИСТОЧНИК] ([RFC 8616](https://www.rfc-editor.org/rfc/rfc8616.html)). Значит, записи заводим на имена вида `_dmarc.xn--719--83dani8b8bqyy.xn--p1ai`.
- **Практика [ВЫВОД]:** `From: "Навигатор ПП 719" <noreply@xn--719--83dani8b8bqyy.xn--p1ai>`. Отображаемое имя кодируется по RFC 2047 (это делает стандартный пакет `email` Python). Кириллическая локальная часть (`код@…`) потребовала бы SMTPUTF8 на всех серверах по пути — у корпоративных серверов палат это не гарантировано. Пользователь, скорее всего, увидит punycode-адрес. Как его покажут Яндекс/Mail.ru/Outlook — **[НЕ ПРОВЕРЕНО]**. Могут ли антифишинговые фильтры занижать оценку punycode-доменов — **[НЕ ПРОВЕРЕНО]**, это риск для пилота. Альтернатива — отдельный ASCII-домен для почты (вопрос владельцу).
- Принимает ли Postbox (и Unisender) IDN-домен при создании адреса — **[НЕ ПРОВЕРЕНО]**. Вводить сразу punycode.

### 2.3 DNS-записи для Postbox [ПЕРВОИСТОЧНИК] ([dns-records](https://yandex.cloud/ru/docs/postbox/concepts/dns-records))

- **DKIM:** при «простой» настройке Postbox сам создаёт ключи и показывает **2 CNAME-записи**. Без DKIM большинство почтовых сервисов отклоняют письма. Статус адреса `Success` — после проверки DNS.
- **SPF:** `v=spf1 include:spf.postbox.yandexcloud.net ~all`. Если SPF на домене уже есть, добавить `include` в неё; запись с `v=spf1` должна быть одна.
- **DMARC:** `_dmarc` → `v=DMARC1; p=none` на старте, затем ужесточать. Адрес отчётов `rua` — ASCII (RFC 8616).
- DNS домена сейчас у Timeweb (`CLAUDE.md`: запись `www` «на парковке Timeweb»). Записи заводить там.

### 2.4 Доставляемость в ящики палат

- Данных о почтовых системах региональных ТПП нет: свои серверы, Яндекс 360 или Mail.ru — **[НЕ ПРОВЕРЕНО]**.
- Риски [ВЫВОД, по RFC 6647 и справке Яндекса выше]:
  - грейлистинг даёт задержку первого письма до десятков минут (RFC 6647);
  - фильтры однотипных писем;
  - карантин писем со ссылками;
  - ящики на `.рф`-доменах.
- План: до запуска отправить пробные письма на 5–10 реальных ящиков палат из разных регионов (с согласия адресатов). Смотреть «Спам», задержку и заголовки `Authentication-Results`. Подключить постмастер-кабинеты Яндекса и Mail.ru. Письмо — только текст и код, без ссылок (или с одной ссылкой на страницу ввода кода), плюс строка «если это были не вы — просто проигнорируйте». Тема, например, «Код входа в Навигатор ПП 719».

## 3. Яндекс ID (OAuth 2.0)

Всё в этом разделе — **[ПЕРВОИСТОЧНИК]**, документация `yandex.ru/dev/id` и Условия, прочитаны 09.10.2026, если не помечено иначе.

- **Регистрация приложения:** [oauth.yandex.ru](https://oauth.yandex.ru/), тип «Для авторизации пользователей» (`https://oauth.yandex.ru/client/new/id/`). Тип после регистрации не меняется. Платформа «Веб-сервисы» → Redirect URI. Дальше выбор данных: логин/имя/фамилия/пол, портрет, email, телефон, дата рождения. Не больше 3 групп разрешений ([register-auth](https://yandex.ru/dev/id/doc/ru/register-auth.md), [register-client](https://yandex.ru/dev/id/doc/ru/register-client.md)).
- **Модерация и верификация:** заявок на модерацию в документации нет. Есть **верификация через Госуслуги**:
  - для организации — добавить её в «Яндекс ID для бизнеса» и подтвердить реквизиты через Госуслуги генерального директора (единоличного исполнительного органа);
  - без верификации пользователи видят предупреждение перед выдачей доступа, «это значительно снижает конверсию»; функциональность ограничена (п. 2.4.7 Условий).
  
  ([confirm-account](https://yandex.ru/dev/id/doc/ru/confirm-account.md), [Условия](https://yandex.ru/legal/authid_api/)). Числа лимитов приложений в документации и Условиях расходятся (5 против 20) — для нас неважно.
- **Требования к программам:** список запрещённых категорий (казино, фишинг, дорвеи и т. п.). Яндекс вправе отказать в доступе без объяснения причин (пп. 2.2, 2.9 Условий) ([requirements](https://yandex.ru/dev/id/doc/ru/requirements.md)).
- **Стоимость:** в Условиях (редакция от 21.08.2026) плата не упоминается. Явной фразы «бесплатно» я не нашёл → **бесплатность — [ВЫВОД]**.
- **Поток:** authorization code.
  - `GET https://oauth.yandex.ru/authorize?response_type=code&client_id=…&redirect_uri=…&state=…&code_challenge=…&code_challenge_method=S256`;
  - **PKCE поддерживается** (S256 предпочтительно, plain допустим);
  - код подтверждения живёт **10 минут**;
  - обмен: `POST https://oauth.yandex.ru/token` (`grant_type=authorization_code`, `code`, `code_verifier`; при переданном `code_verifier` секрет «передавать не требуется»);
  - `state` до 1024 символов, документация сама предлагает его для защиты от CSRF.
  
  ([code-url](https://yandex.ru/dev/id/doc/ru/codes/code-url.md)). У нас серверное приложение, поэтому [ВЫВОД]: PKCE **и** `client_secret` вместе, `state` в сессии.
- **Redirect URI:** у адреса в запросе и в настройках должны совпадать схема, хост, порт и путь; query и fragment могут отличаться ([register-auth](https://yandex.ru/dev/id/doc/ru/register-auth.md)). Принимает ли кабинет кириллический хост — **[НЕ ПРОВЕРЕНО]**. Регистрировать punycode: `https://xn--b1afk4ade.xn--719--83dani8b8bqyy.xn--p1ai/auth/yandex/callback` — браузер ходит по домену именно в этом виде (`app/core/config.py`, комментарий к `APP_SUBDOMAIN`). Возврат с Яндекса — top-level GET, поэтому кука сессии с Lax на нём придёт ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)).
- **Данные пользователя:** `GET https://login.yandex.ru/info?format=json`, заголовок `Authorization: OAuth <токен>` (передавать токен параметром URL не рекомендуется) ([user-information](https://yandex.ru/dev/id/doc/ru/user-information.md)).
  - **Без запрошенных прав** приходят `login`, `id`, `client_id`, `psuid`. Для привязки этого достаточно, и это минимально по данным (п. 2.4.1 Условий требует «минимально необходимого состава»).
  - С правом «Адрес электронной почты» — `default_email` («для связи с пользователем») и `emails`.
  - Идентификаторы прав в формате `login:info login:email login:avatar` видны в примере ответа [ПЕРВОИСТОЧНИК]. Точные строки для телефона и даты рождения я в документации не нашёл — **[НЕ ПРОВЕРЕНО]**.
- **Подтверждён ли email:** признака подтверждения в ответе нет. Условия, п. 4.5: «Яндекс не осуществляет проверку достоверности, актуальности, точности и корректности Данных Яндекс ID» → **автопривязку к учётке по `default_email` не делать** [ВЫВОД].
- **Кнопка/SDK:**
  - «мгновенная авторизация» (виджет или кнопка, `sdk-suggest.js`) работает через `response_type: 'token'` и вспомогательную страницу с `postMessage`;
  - не работает без JS и iframe, виджет — без сторонних cookie ([script-sdk-suggest](https://yandex.ru/dev/id/doc/ru/suggest/script-sdk-suggest.md), [suggest-description](https://yandex.ru/dev/id/doc/ru/suggest-description.md)).
  
  [ВЫВОД]: нам проще и безопаснее обычный редирект с серверным обменом кода и статичная кнопка («Конструктор кнопок» есть в документации). Сторонний скрипт на страницу входа не нужен.
- **Срок жизни токена** зависит от прав («не менее 1 года» в примере). Нам неважно: токен не храним ([концепции](https://yandex.ru/dev/id/doc/ru/concepts/ya-oauth-intro.md)).
- **Риски [ВЫВОД]:**
  1. У части сотрудников палат нет Яндекс-аккаунта или они не хотят смешивать личный аккаунт с рабочим. Доля не измерена.
  2. Личный аккаунт не «уходит» вместе с сотрудником, в отличие от корпоративного ящика: увольнение приходится обрабатывать вручную.
  3. Яндекс может отключить приложение в одностороннем порядке (пп. 2.2, 2.9).
  4. Корпоративные политики палат по сторонним аккаунтам — **[НЕ ПРОВЕРЕНО]**.
  5. Без верификации организации пользователи видят предупреждение.

Источник: [КонсультантПлюс, ст. 8 149-ФЗ](https://www.consultant.ru/document/cons_doc_LAW_61798/78b773a28f3ad19eb234697b20ab1d48c09f748a/), редакция от 26.06.2026. Часть введена 406-ФЗ от 31.07.2023, п. 1 изложен в редакции 588-ФЗ от 12.12.2023. Цитата:

> 2) с использованием федеральной государственной информационной системы "Единая система идентификации и аутентификации …";
> 3) с использованием государственной информационной системы "Единая система идентификации и аутентификации физических лиц с использованием биометрических персональных данных" в порядке, предусмотренном статьями 9 и 10 Федерального закона от 29 декабря 2022 года N 572-ФЗ …;

### 4.2 Ответственность: ст. 13.55 КоАП [ПЕРВОИСТОЧНИК]

### 4.3 Относится ли к закрытому B2B-сервису, где учётки выдаёт администратор

- **По тексту — да.** Условие применения — «доступ к информации … предоставляется пользователям, прошедшим авторизацию». Исключений для корпоративных или закрытых систем в ч. 10 ст. 8 нет [ПЕРВОИСТОЧНИК, §4.1].
- Комментаторы к тому же выводу: колонка ppt.ru относит к адресатам «владельцев информационных систем (CRM, корпоративные порталы, онлайн-сервисы)» ([ppt.ru, 16.06.2026](https://ppt.ru/columns/jurist-v-it/otvetstvennost-za-narushenie-pravil-avtorizatsii-i-rekomendatelnykh-tekhnologiy)). Автор на Хабре: «Почему не сделано исключение для корпоративных систем - непонятно» ([Хабр](https://habr.com/ru/articles/1046183/)) [ВТОРИЧНЫЙ].
- **«Пробный режим» без входа:** если информация доступна без авторизации, ч. 10 ст. 8 к этому режиму не применяется. Гарант: «Если весь контент сайта или приложения доступен неавторизованным пользователям, добавлять систему авторизации необязательно» ([Гарант](https://www.garant.ru/article/2136195/)) [ВТОРИЧНЫЙ; следует и из текста нормы — ВЫВОД]. Регистрация из гостя должна идти разрешённым способом.

## 6. Набросок реализации (план, без кода)

### 6.1 Данные

- `users` (через `_ensure_columns`):
  - `login_email VARCHAR(255)`, `login_email_verified_at DATETIME`, `auth_epoch INTEGER DEFAULT 0`, `password_login_disabled BOOLEAN DEFAULT 0`;
  - отдельно `CREATE UNIQUE INDEX IF NOT EXISTS ix_users_login_email ON users(login_email)`. NULL'ы в SQLite уникальность не нарушают.
- ⚠ **Не использовать для входа редактируемый `users.email` кабинета.** Иначе любой, кто хоть раз получил доступ к сессии (чужой компьютер, оставленная вкладка), сменит адрес на свой и навсегда заберёт учётку. Без уникальности ещё и два аккаунта окажутся на одном адресе.
  - Вариант 1 (проще): `email` кабинета остаётся контактом, а вход живёт в `login_email`.
  - Вариант 2: одно поле, но правка только через код на **новый** адрес плюс уведомление на старый.
  
  Кабинет (`68df2c4`) сделан по варианту 1: «Рабочий email» — контакт. Вход по коду, если его заведут, — отдельное подтверждённое поле `login_email`.
- Новая таблица `login_codes` (поля в §1.7). Очистка просроченных — при каждом запросе кода, как `purge_old_leads`.
- Второй этап: таблица `user_identities` (provider, subject, user_id, linked_at; уникальность по provider+subject).

### 6.2 Настройки (`app/core/config.py` + `.env.example` — их сверяет `TestEnvExampleMatchesSettings`)

- `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM` (в punycode), `MAIL_FROM_NAME`, `MAIL_REPLY_TO`.
- `LOGIN_CODE_SECRET` — отдельно от `SESSION_SECRET`; в проде, как и `SESSION_SECRET`, не стартовать с дефолтным.
- `LOGIN_CODE_TTL_MIN=10`, `LOGIN_CODE_MAX_ATTEMPTS=5`, `PASSWORD_LOGIN_ENABLED=true`.
- Этап 2: `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`.
- `MAIL_BACKEND=smtp|console|memory` — в тестах и разработке письма не уходят наружу.

### 6.3 Эндпоинты

- `GET /login` — форма email (основная), ссылка «Войти по логину и паролю», которая показывается, пока `PASSWORD_LOGIN_ENABLED`. Этап 2 — кнопка «Войти с Яндекс ID».
- `POST /login/code` — запрос кода → 303 на `GET /login/code`. Лимиты по IP (`SlidingWindow`) и по адресу (счёт в `login_codes`).
- `GET /login/code` — ввод кода, маскированный адрес, «отправить ещё раз».
- `POST /login/code/verify` — проверка → вход (+ remember) → гейт профиля как сейчас.
- `POST /login/code/resend`.
- `POST /login` — пароль остаётся, но для `password_login_disabled` или при выключенном `PASSWORD_LOGIN_ENABLED` отвечает той же ошибкой, что и на неверный пароль (без подсказки). Для `admin` после пароля — шаг кода на `login_email` (второй фактор).
- Кабинет: блок «Способы входа» — подтвердить или сменить email для входа (код на новый адрес, уведомление на старый). Этап 2 — привязать или отвязать Яндекс ID (только из залогиненной сессии).
- `/admin`: колонка «email для входа / подтверждён», поле задать или сменить, кнопка «отправить приглашение». Создание учётки из заявки — по решению владельца.
- Этап 2:
  - `GET /auth/yandex/start` — state + PKCE (S256) в сессию → редирект на `oauth.yandex.ru/authorize`;
  - `GET /auth/yandex/callback` — сверка state → `POST oauth.yandex.ru/token` (code_verifier + секрет) → `GET login.yandex.ru/info` → поиск в `user_identities`. Не найдено и не залогинен — страница «Аккаунт Яндекса не привязан: войдите по коду на рабочую почту и привяжите его в кабинете». Автосоздания нет. Токен не сохраняется.
- «Запомнить меня»: в подписанный токен класть `(user_id, auth_epoch)` и при чтении сверять с БД. «Выйти на всех устройствах», смена email для входа и отключение учётки увеличивают `auth_epoch`. Это закрывает нынешнюю неотзываемость 30-дневной куки.

### 6.4 Сосуществование с паролем (переходный период)

1. Релиз 1: код на email работает для учёток с `login_email`, пароль — для всех. Admin вносит адреса для 28 учёток или рассылает приглашения.
2. Релиз 2 (через 2–4 недели, по журналу входов): `password_login_disabled=1` для `user`, у кого адрес подтверждён. Пароль остаётся у `admin` как фактор вместе с кодом.
3. Релиз 3: `PASSWORD_LOGIN_ENABLED=false` для всех, кроме admin. `seed_users.py` выдаёт учётки по email без пароля.
4. «Гость → регистрация» (когда появится пробный режим): тот же `POST /login/code` с `purpose=signup` для незнакомого адреса. Правила самостоятельной регистрации — решение владельца (§7).

### 6.5 Тесты (офлайн, как вся батарея; отправка — через `MAIL_BACKEND=memory`)

- **Код:** 6 цифр; в БД нет открытого кода (только HMAC); срок истекает (подмена времени); после 5 неверных вызов сгорает; одноразовость; новый код гасит старый; сравнение через `compare_digest`.
- **Привязка к сессии:** верный код из чужой сессии (без cookie вызова) не работает; `POST /login/code/verify` без cookie — отказ (login CSRF).
- **Перечисление:** известный и неизвестный адрес дают одинаковый статус, тело и редирект. Письмо отправлено только известному (или письмо «нет аккаунта» — по решению). Отправка не в пути запроса.
- **Лимиты:** по адресу (60 с, 5/ч, 20/сут, переживают перезапуск — счёт в БД); по IP; `Retry-After`.
- **Нормализация:** регистр, пробелы, кириллический домен → A-label; уникальность `login_email` (дубль → понятная ошибка в админке).
- **Вход и гейты:** после входа по коду роль `user` без профиля попадает на `/profile`; `admin` — в чат; `remember` ставит куку; рост `auth_epoch` гасит старую remember-куку.
- **Переход:** пароль работает, пока включён; при `password_login_disabled` — та же ошибка, что на неверный пароль; admin с паролем без кода не входит.
- **Письмо:** `From` ASCII/punycode; отображаемое имя по RFC 2047; ссылки (если есть) строятся из настроек, не из `Host` (тест с подменённым `Host`); код не попадает в журнал (`loguru`).
- **Кабинет:** смена email для входа требует кода на новый адрес и шлёт уведомление на старый; редактируемый контактный `email` вход не меняет.
- **Яндекс ID (этап 2):** state не совпал → 400; в запросе есть `code_challenge` (S256), при обмене — `code_verifier`; неизвестный `id` не создаёт учётку; привязка — только из залогиненной сессии; токен не сохраняется; `default_email` не используется для автопривязки.
- **Документы:** `TestEnvExampleMatchesSettings`; публичность `/privacy` и новой страницы согласия; дата редакции обновлена.
- По практике проекта — мутации на ключевые проверки: убрать лимит, убрать сравнение сессии, хранить код открыто — тест должен падать.

## 7. Открытые вопросы владельцу

1. **Кто юридический владелец сайта и оператор ПДн** — Курская ТПП, ИП/ООО разработчика или физлицо? От этого зависят размер штрафа по 13.55 (юрлицо 500–700 тыс. ₽, гражданин 10–20 тыс. ₽), проверка «российского юрлица» по п. 4 и текст согласия. Сейчас в политике оператором стоит `{{ org }}` = `ORG_NAME`, «Курская ТПП».
2. **Подано ли уведомление в РКН** об обработке ПДн и кем? Если да — его нужно обновить до 15-го числа месяца после запуска входа по email.
3. Готовы ли получить **заключение юриста** по коду на email как «иной ИС», или сразу закладываем Яндекс ID (или SMS) как обязательный второй способ?
4. **Самостоятельная регистрация гостя:** любой email, только домены палат (список доменов?) или только после одобрения заявки?
5. **Что получает неизвестный адрес:** ничего или письмо «аккаунта нет — оставьте заявку»?
6. **Адрес отправителя:** `noreply@719-навигатор.рф`, который получатели увидят в punycode, или отдельный ASCII-домен для почты? Куда идут ответы (Reply-To, живой ящик поддержки)?
7. **Провайдер:** Postbox (тот же облачный аккаунт) или Unisender Go?
8. **Срок отключения пароля** для роли `user`. Оставляем ли администраторам пароль плюс код?
9. **Кто соберёт рабочие email** 28 действующих учёток (таблица «логин → человек» офлайн)?
10. **«Рабочий email» кабинета (ветка `feat/auth-account`)** — это и есть email для входа (тогда правка только через код) или отдельный контакт?
11. **Яндекс ID:** пройдёт ли руководитель организации верификацию через Госуслуги («Яндекс ID для бизнеса»)? Без неё пользователи видят предупреждение.
12. «Запомнить меня» после входа по коду включать **по умолчанию**? Иначе код придётся вводить при каждом открытии браузера — сессионная кука `max_age=None`.
