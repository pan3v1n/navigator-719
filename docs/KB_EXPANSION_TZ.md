# ТЗ — расширение базы знаний и адаптация архитектуры RAG

> **Назначение.** План работ на следующий этап: довести архитектуру RAG до состояния, в котором
> корпус можно расширять нормативными документами без правки кода и без потери качества, и
> добавить документы, которых требуют отзывы региональных ТПП.
>
> **Когда начинать.** После завершения текущей волны доработок по ревью (`REVIEW_TZ.md`, задачи R1–R27).
> Расширение базы знаний (волна D) начинается **в новой сессии** и только после закрытия K8, K9, K11.
>
> **Визуальная схема (состояние → цель → документы → план):**
> https://claude.ai/code/artifact/1725ae36-a895-4022-b39f-0ceb078ade7c
> Исходник страницы — [docs/architecture.html](architecture.html), редактируется и перепубликуется.
>
> **ID задач:** `K1…K17` (`K` = knowledge base) — не пересекаются с `T1…T18`
> ([POST_TEST1_TZ.md](POST_TEST1_TZ.md)) и `R1…R27` ([REVIEW_TZ.md](REVIEW_TZ.md)).

## 1. Резюме и порядок работ

Задач: **17**, сгруппированы в четыре волны. Волна R (доработки по ревью) идёт параллельно и здесь
не затрагивается.

| Волна | Смысл | Задачи | Когда |
|---|---|---|---|
| **A** Товарная ось — данные | Закрывает провал приёмки: 26 % позиций без требований, 53 % без порога | K1–K4 | после R |
| **B** Ретрив | Дешёвые улучшения поиска, делаются одной переиндексацией с A | K5–K7 | вместе с A |

**Соответствие меток артефакта и ID:** A1→K1, A2→K2, A3→K3, A4→K4 · B1→K5, B2→K6, B3→K7 ·

## 2. Принцип, на котором стоит весь план

**Механизм обслуживания выбирается по природе знания, а не по тому, что источник пришёл файлом.**

| Класс знания | Что относится | Механизм |
|---|---|---|
| Факты-таблицы | приложение 719 (позиции, операции, баллы, пороги), сквозные требования, перечень условий по ТН ВЭД, тарифы | нормализованный слой + детерминированный lookup; Qdrant — индекс навигации, не источник чисел |
| Классификаторы | ОКПД2, ТН ВЭД, переходные ключи, справочник документов ТПП | таблицы на диске, прямой доступ, 0 ₽ |
| Нормы-проза | тело ПП №719, Правила реестра, Приказ ТПП №52, СТ-1, Методрекомендации, ГИСП | RAG с фильтрами по теме, источнику, статусу и редакции |
| Практика | кейсы эксперта, FAQ, типовые отказы | отдельная коллекция, высший приоритет, пометка «не норма» |

Перечень условий по кодам ТН ВЭД, приложение с тарифами и справочник документов ТПП придут
нормативными документами, но по природе это **таблицы фактов**. Если положить их в векторный индекс
как прозу, мы воспроизведём на новом корпусе ровно тот дефект, который сейчас лечим в приложении 719.

## 3. Волна A — товарная ось (данные)

### `[ ]` K1 — Наследование требований по группам · **P0** · ~1 сессия

**Проблема.** 360 записей из 1 379 (**26 %**) не имеют ни одной операции требований:
`requirement_blocks: []`. Это дочерние строки групп — требования лежат у родителя, а модель
хранения «одна позиция = одна точка» наследования не даёт. Больше всего пострадали XVIII
Судостроение (101), XXI Нефтегазохимия (84), VII Медизделия (35). Поиск такую позицию находит,
а показать нечего.

**Что сделать.** При подготовке данных разворачивать наследование в payload дочерней записи с явной
пометкой происхождения («унаследовано от группы N»), чтобы эксперт видел, откуда требование.
Не в рантайме — в индексации, иначе каждый ответ платит за обход иерархии.

**Критерий приёмки.** Позиций с пустым списком требований — не более 5 % (остаток = позиции, у
которых требований нет и в первоисточнике). Пометка происхождения видна в ответе. Регресса
`eval_coverage` нет.

**Файлы.** `scripts/structure_kb.py`, `scripts/rechunk_appendix.py`, `scripts/load_kb.py`.

### `[ ]` K2 — Разрешение ссылок на примечания при индексации · **P0** · ~1 сессия

**Проблема.** Своего `min_threshold` нет у 1 140 записей (**83 %**); `thresholds.lookup_threshold`
восстанавливает часть эвристикой из плоских списков (196 строк), остальное уходит в ответ как
«Порог: в контексте не указан». Эксперты в отзывах называют **семь конкретных примечаний**:
**7, 11, 29, 31, 52, 53, 55** — например, «В Примечании 7 ПП 719 указан порог для продукции с кодом
22.22 — не менее 90 баллов», «Порог указан в п. 29 Примечаний», «д. б. отсылка на Примечание № 53 с
условием выполнения требований, предусмотренных разделом XVII».

**Что сделать.** Паттерн cross-reference resolution: распознать ссылку на примечание у позиции,
разрешить её **на этапе индексации** и вшить текст примечания в payload и в текст для sparse-канала.
Эвристический рантайм-lookup после этого становится фолбэком, а не основным путём.

**Критерий приёмки.** Все семь названных экспертами примечаний корректно подтягиваются к своим
позициям (готовый приёмочный набор). Доля позиций без порога — не более 20 %. Числа порога
заземлены для faithfulness-гарда (то есть присутствуют в контексте дословно).

**Файлы.** `app/rag/thresholds.py`, `scripts/structure_kb.py`, `scripts/load_kb.py`.

### `[ ]` K3 — Детерминированная контекстуализация чанков · **P1** · ~0.5 сессии

**Проблема.** Строка «29.10.59.310» без контекста своей группы не самодостаточна: ни dense, ни
sparse не понимают, о чём она. Публичная практика (Contextual Retrieval) решает это генерацией
50–100 токенов контекста на чанк через LLM — с заявленным сокращением ошибок ретрива до 49 %
вместе с BM25.

**Что сделать.** Нам генерация не нужна: **контекстный заголовок собирается из уже имеющейся
структуры** — раздел, родительская группа, унаследованный порог, номера примечаний. Получаем эффект
приёма без вызовов модели, без стоимости и без риска галлюцинаций в самом индексе.

**Критерий приёмки.** `eval_coverage` и `eval_paraphrase` не хуже базы; целевой замер — рост
`recall@1` на перефразированных запросах.

**Файлы.** `scripts/load_kb.py` (`build_embedding_text`).

### `[ ]` K4 — Слой сквозных требований · **P0** · ~1 сессия

**Проблема.** Требования, применимые ко **всем** позициям сразу, не привязаны ни к одной и потому
не показываются. В отзывах это один из самых частых классов претензий:

- «Не приведено требование: наличие у субъекта деятельности — налогового резидента стран — членов
  ЕАЭС **прав на использование нормативно-технической документации** в объёме, достаточном для
  производства» — обязательное требование, балльной оценки нет (4 упоминания);
- «Отсутствует отсылка на обязательность осуществления указанных тех. операций **на территории
  Российской Федерации**», «операции должны осуществляться в РФ или можно ещё в ЕАЭС?» — **15
  упоминаний**;
- «пропущена ключевая фраза: осуществление на территории РФ с 1 января 2020 г. всех следующих
  технологических операций…».

**Что сделать.** Извлечь такие нормы из тела и примечаний (они **уже в корпусе**, внешний источник
не нужен) в отдельный слой сквозных требований и подмешивать его в каждый товарный ответ независимо
от найденной позиции. Обязательные требования без баллов выводить отдельным блоком от балльных.

**Критерий приёмки.** На приёмочных кейсах из отзывов ответ содержит требование о правах на НТД и
условие о территории выполнения операций. Обязательные требования не помечаются как балльные.

**Файлы.** новый модуль в `app/rag/`, `app/rag/pipeline.py` (`format_context`), `app/core/prompts.py`.

## 4. Волна B — ретрив

### `[ ]` K5 — Асимметричный гибрид: dense по идентичности, sparse по полному тексту · **P1** · ~2 часа

**Проблема.** `build_embedding_text` кладёт в вектор только идентичность (имя, раздел, код, порог) —
и **тот же текст идёт в оба канала**. Для dense это обосновано замером (product-level recall@1
0.886 → 0.972), но BM25 при этом потерял единственный смысл: лексический поиск по формулировкам
требований («закалка зубьев», «пайка волной») невозможен ни по одному каналу.

**Что сделать.** `dense` — из `build_embedding_text`, `sparse` — из `build_text` (обе функции уже
существуют). Меняется один аргумент в `index_all`; схема коллекции не трогается.

**Критерий приёмки.** Запрос по формулировке операции находит позицию, которая сейчас не находится.
`eval_coverage` и `eval_golden` без регресса.

**Файлы.** `scripts/load_kb.py` (`index_all`).

---

### `[ ]` K6 — Бюджет контекста вместо капов на хит · **P1** · ~0.5 сессии

**Проблема.** Сейчас 8 хитов × до 60 операций у целевого (`MAX_OPS_TARGET`) и по 12 у прочих. По
экономике июля: **93 % токенов — входные** (4.48 млн из 4.80 млн), в среднем 7 940 токенов на ответ.
Деньги не проблема (≈140 ₽/мес), но контекст разбавляется: целевая позиция тонет среди семи прочих
кандидатов.

**Что сделать.** Фиксированный бюджет на весь контекст с приоритетом целевого хита; хвост кандидатов
сворачивать в одну строку «прочие кандидаты: коды и наименования».

**Критерий приёмки.** Средний размер входного контекста снижается; `eval_determinism` (стабильность
чисел) и `eval_answers` не хуже, целевой эффект — рост детерминизма на мега-продуктах.

**Файлы.** `app/rag/pipeline.py` (`format_context`, константы `MAX_OPS_*`).

---

### `[ ]` K7 — Реранкер: замерить cross-encoder против LLM-rerank · **P2** · ~0.5 сессии

**Проблема/контекст.** Сейчас реранк — вызов DeepSeek (`app/rag/reranker.py`), включается только при
отсутствии совпадения по коду. Публичная практика говорит, что cross-encoder дешевле, быстрее и не
хуже. Но на 2 vCPU multilingual cross-encoder — порядка 40 мс на пару, то есть ~2 с на 50 кандидатов,
плюс скачивание модели упирается в ту же рваную сеть, из-за которой мы держим локальный BM25.

**Что сделать.** Замерить на `eval_retrieval`, решение принять по цифрам. LLM-rerank оставить
фолбэком в любом случае.

**Критерий приёмки.** Есть замер и решение, зафиксированное в этом файле. Выигрыш неочевиден заранее —
отрицательный результат тоже результат.

## 5. Волна P — подготовка корпуса к расширению

### `[ ]` K8 — Паспорт записи + манифест корпуса + статус и срок действия · **P0** · ~1 сессия

**Проблема.** В коллекции `pp719_rules` три документа разной юридической силы лежат плоско.
`edition` штампуется, но `valid_from` / `valid_to` / `status` нет: утратившие силу «Правила выдачи
заключения» исключены **вручную, решением не индексировать**. В отзывах уже есть «Приведена ссылка на
недействующую редакцию ПП №719» и «Ссылается на устаревшие редакции нормативных документов».

**Что сделать.** Ввести паспорт записи:

```yaml
doc_id:        prikaz_tpp_52
authority:     ТПП РФ          # Правительство РФ | ТПП РФ | ЕЭК | Минпромторг | СНГ
legal_force:   3               # 1 постановление · 2 правила/приложение · 3 ведомственный акт
                               # 4 разъяснение · 5 практика
doc_type:      процедура       # процедура | критерии | состав документов | классификация
topic:         документы       # реестр | документы | СТ-1 | акт | ГИСП | компоненты
key_type:      null            # ОКПД2 | ТН ВЭД | null  ← см. K14
point:         "п. 4.2"
edition:       "ред. от 01.07.2026"
valid_from:    2026-07-01
valid_to:      null
status:        действует       # действует | утратил силу | не вступил
supersedes:    prikaz_tpp_41
source_anchor: "Приказ ТПП РФ №52, п. 4.2"   # уже есть
```

И манифест `knowledge_base/manifest.yaml` — единственный источник правды о составе корпуса: какие
документы загружены, какой редакции, что действует. Загрузчик читает манифест, а не хардкод путей.

**Критерий приёмки.** Все 242 существующих пункта имеют заполненный паспорт. Запись со
`status: утратил силу` не попадает в контекст ни при каком запросе (юнит-тест). Манифест описывает
текущий корпус полностью.

**Файлы.** `scripts/load_rules_kb.py`, `app/rag/retriever.py` (`search_rules`), новый `knowledge_base/manifest.yaml`.

### `[ ]` K9 — Процедурный golden set · **P0** · ~0.5 сессии

**Проблема.** В `scripts/eval_golden.json` **ноль** процедурных кейсов. Самая быстрорастущая часть
базы не покрыта ни одной метрикой: добавление документа может тихо ухудшить ответы по соседнему.

**Что сделать.** Набор процедурных кейсов с ожидаемым источником ответа (не текстом, а `doc_id` +
пунктом) — по 5–10 на каждый документ корпуса. Метрика: **атрибуция источника** — пришёл ли ответ из
того документа, из которого должен.

**Критерий приёмки.** ≥ 20 процедурных кейсов на текущие три документа; метрика атрибуции считается
и записана как база отсчёта. Дальше каждый новый документ приходит со своими кейсами (см. K14–K17).

**Файлы.** `scripts/eval_golden.json` или новый `scripts/eval_golden_rules.json`, `scripts/eval_*.py`.

### `[ ]` K10 — Фильтр по `doc_type` / `topic` + квота на источник · **P0** · ~2 часа

**Проблема.** `search_rules` делает плоский `top-6` по всей коллекции **без единого фильтра**, хотя
индекс по `doc_type` создан в `recreate_collection` и **не используется ни разу**. При вопросе «какие
документы готовить» пункты Приказа №52 могут не добраться в окно — их вытеснит более многословный
документ. Эксперты трижды прямо спрашивали про Приказ №52: «Почему нигде нет ссылки на положение об
экспертизе по Приказу 52 ТПП РФ?».

**Что сделать.** Фильтр по теме вопроса + квота на источник: каждый релевантный теме документ
получает гарантированное место в окне контекста.

**Критерий приёмки.** На вопросе о составе документов в контексте присутствуют и Приказ №52, и тело
постановления. Метрика атрибуции из K9 не падает.

**Файлы.** `app/rag/retriever.py` (`search_rules`), `app/rag/pipeline.py` (`_answer_procedural`).

### `[ ]` K11 — Инкрементальная переиндексация по `doc_id` · **P0** · ~0.5 сессии

**Проблема.** `recreate_collection` удаляет коллекцию целиком: добавление одного приказа
переиндексирует все 242 пункта. При восьми документах это станет тормозом на каждой правке.

**Что сделать.** Upsert по `doc_id` с предварительным удалением точек этого документа по фильтру;
полная пересборка — отдельным явным флагом.

**Критерий приёмки.** Добавление документа не изменяет точки остальных документов (проверяется
сравнением количества и идентификаторов до/после).

**Файлы.** `scripts/load_rules_kb.py`.

### `[ ]` K12 — Тематический роутер вместо бинарного · **P1** · ~1 сессия

**Проблема.** `procedural.is_procedural` отвечает на вопрос «товар или процедура». Внутри «процедуры»
уже сейчас минимум четыре разных намерения: внести в реестр · какие документы собрать · путь СТ-1 и
страна происхождения · как классифицировать продукцию. Все обслуживаются одним промптом и одним окном.

**Что сделать.** Шесть тем: товар · реестр · документы и сроки · СТ-1 и происхождение · классификация
кода · вне сферы. Детерминированно (регулярки), как сейчас; каждая тема даёт свой фильтр (K10) и свой
фрагмент промпта.

**Критерий приёмки.** Свип по реальным запросам из выгрузки: доля верной темы ≥ 0.9, ложных
срабатываний на товарных запросах — ноль (как в текущем свипе: 0 ложных на 104).

**Файлы.** `app/rag/procedural.py`, `app/core/prompts.py`.

### `[ ]` K14 — Корпус СТ-1 и второй ключ классификации · **P0** · ~1–2 сессии

**Почему первым.** Самый частый документный запрос в отзывах — **26 упоминаний**. Эксперты
формулируют ожидаемое поведение дословно: «у вас итоговый документ скорее всего СТ-1 и попросить код
ТН ВЭД указать», «диалог в тупике, ИИ не даёт вариант, что у вас СТ-1 и требования по коду ТН ВЭД
необходимо смотреть», «укажите ваш код ТН ВЭД, распишу требования».

**Архитектурное следствие.** Требования по СТ-1 живут **в разрезе ТН ВЭД**, а весь корпус построен
на ОКПД2. Это не «ещё один документ», а **второй ключ классификации**: паспорт записи несёт
`key_type`, роутер понимает, по какому ключу отвечать, мост между ключами уже есть —
`knowledge_base/classifiers/tnved_okpd2.tsv`.

**Критерий приёмки.** На кейсе «продукции нет в приложении 719» ответ предлагает путь СТ-1, просит
или выводит код ТН ВЭД и показывает условия достаточной переработки по этому коду. 5–10 приёмочных
кейсов добавлены в набор K9.

### `[ ]` K15 — Методические рекомендации ТПП + справочник документов · **P0** · ~1 сессия

**Почему.** «Какие документы готовить» — **самая частая тема отзывов (31 упоминание)**. Показательно:
сам документ по названию в отзывах не упоминается ни разу — приоритет обоснован спросом на
*содержание*, а не на *название*.

Справочник документов закрывает отдельный дефект: модель выдумывала несуществующее «заключение ТПП»
(**6 упоминаний**), при том что эксперты дважды дали закрытый перечень: «В текущей редакции положения
есть — СТ-1, Акт экспертизы ТПП и сведения о реестровой записи с приложением выписок из реестра».
Держать это надо жёстким справочником, а не правилом промпта.

**Критерий приёмки.** На вопрос о составе документов ответ ссылается на Методрекомендации и Приказ
№52. Термин «заключение ТПП» не появляется ни в одном ответе (юнит-тест).

## 8. Что решено НЕ делать

| Приём | Почему не нам |
|---|---|
| HyDE / query expansion | По замерам устойчивости RAG: +2.61 % на варьированных запросах, но **−5.43 % на исходных**. Наш трафик — прямые вопросы о продукции |
| GraphRAG | Корпус 1 379 + 242 записи; глобальных многодокументных вопросов нет |
| Миграция на LlamaIndex ради parent/child | Иерархия дешевле решается на слое данных, чем импортом фреймворка ради одного паттерна |
| Семантический чанкинг | Структура документов известна точно; семантическая нарезка её ухудшит |
| Коллекция на каждый документ | Размножает код, ломает единую калибровку IDF и убивает кросс-документные ответы. Одна коллекция на **класс знания**, документы внутри — фильтрами |
| Агрессивное кэширование ради экономии | 140 ₽/мес и 604 ответа за месяц — экономия не окупает сложности |
| Смена эмбеддера вслепую | FRIDA (0.8B) против e5-large (560M): рост RAM и латентности на CPU-VM. Решать только по A/B на нашем харнесе |
