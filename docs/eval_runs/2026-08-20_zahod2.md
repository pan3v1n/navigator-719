## Приёмка захода 2

### ✅ `D12` #90 — исключённые позиции ушли из корпуса

Запрос по коду `14.12.30.131` (самого кода в корпусе НЕТ) во всех трёх формах — голый код,
«требования для …», «какие требования по коду …» — даёт **№1 «Спецодежда» (`14.12`, раздел XVII)
с совпадением по коду**, добранную по иерархии. Заглушек с наименованием-формулой требования
в выдаче нет.

⚠ **Проверять надо через тот же путь, что и рантайм.** Первая проба звала
`retriever.search(q)` без `okpd2` и дала мусор (top-1 «Столы обеденные» — совпадение по хвосту
«131» в `31.09.12.131`). Буст по коду включается только при переданном `okpd2`, который
пайплайн получает из `extract_okpd2`. Диагностический инструмент, не повторяющий рантайм,
показывает несуществующий дефект — тот же урок, что и с обрезанными якорями 16.08.

### ✅ `K2` #47 — закупочный порог больше не выдаётся за общий

Проверено по всему корпусу: **510** позиций получают порог из **25** различных примечаний,
и **ни одна — из закупочного** (0 из 510). Это критерий, закрывающий самый дорогой класс
дефекта: правильное число из первоисточника, привязанное не к тому вопросу.

### ❌ `K2` #47 — доля «без общего порога ≤22 %» НЕ ПОДТВЕРЖДАЕТСЯ

**Числа `24.6 % → 18.4 %`, которыми задача принята 19.08, воспроизвести нечем и не удалось.**
Кода, считающего эту величину, в репозитории не было ни одного: она существует только в
сообщении коммита `e939e0f` и в документах. Ни один тест её не закрепляет.

Заведён `scripts/eval_threshold_coverage.py`, повторяющий порядок разрешения порога из
рантайма (`pipeline.format_context`): своё `min_threshold` → блок → примечание
(`lookup_threshold`) → порог группы через наследование, причём закупочный порог общим не
считается. Одна и та же метрика на обеих ветках:

| Срез | `main` (до захода 2) | `dev` (после) | Δ |
|---|---|---|---|
| **points + mixed** | 408/881 = **46.3 %** | 351/880 = **39.9 %** | **−6.4 п.п.** |
| весь корпус | 719/1381 = **52.1 %** | 609/1377 = **44.2 %** | −7.9 п.п. |
| порогов добрано из примечаний | 401 | **510** | +109 |

Проверены четыре разумных определения метрики — весь корпус (44.2 %), `points`+`mixed`
(39.9 %), только позиции с реальными баллами (34.0 %), без учёта наследования и блоков
(45.8 %). **Ни одно не даёт 18.4 %**; расхождение с заявленным — примерно вдвое.

**Что из этого следует и что НЕ следует.**
* Правка `K2` **работает**: заявленная дельта −6.2 п.п. (24.6 → 18.4) почти точно совпадает с
  измеренной **−6.4 п.п.** Улучшение реально, направление верное, механизм добора порогов цел.
* **Не подтверждается уровень**, а вместе с ним — вывод «достигнуто 18.4 %, ниже и нового
  порога ≤22 %, и прежнего ≤20 %». На воспроизводимом определении корпус стоит около 40 %,
  то есть критерий приёмки `K2` **не выполнен**, а не выполнен с запасом.
* Это ровно тот случай, о котором говорит собственный урок проекта: критерий приёмки,
  построенный на числе, которое нельзя пересчитать, наследует все дефекты этого числа.
  Пока определение не зафиксировано кодом, «≤22 %» нечем ни подтвердить, ни опровергнуть.

**Что делать:** признать долей истину замера (либо предъявить определение, дающее 18.4 %, —
тогда закрепить его тем же скриптом), поправить число в `BACKLOG`, `KB_EXPANSION_TZ` и
`NEXT_SESSION`, и держать `eval_threshold_coverage.py` в уровне 0.
