# R31-2 #245 — окно плавало между прогонами: ничья score в пересчёте `R31` решалась случаем (28.10.2026)

**Вопрос.** Замер `EV8-1` (27.10) показал: два прогона `retriever.search` подряд, один вопрос и код — разная
целевая позиция («Краски полиграфические 20.30.24»: XXI/27 ↔ XXI/30). Подозрение — пересчёт score окна
`_rescore` (`R31` #179). Выпускать ли `R31` в `test43`?

**Причина — найдена прямым опытом.** Пересчёт шёл одним гибридным запросом `FusionQuery(RRF)` по id
кандидатов. У XXI/27 и XXI/30 sparse-score равны до бита (16.110046), и Qdrant раздаёт этой ничьей ранги
в произвольном порядке: за 12 прогонов первой была XXI/27 7 раз, XXI/30 — 5. RRF складывает ранги, поэтому
ничья в одном списке превращается в разные суммы, и `_order_key` (тай-брейк по якорю — только при РАВНОЙ
сумме) их уже не выравнивает. Отдельные запросы dense и sparse с тем же фильтром за 8 прогонов порядок не
меняли — плавает именно ранжирование ничьих внутри слияния.

**Правка.** Слияние — на нашей стороне (`retriever._rrf_tied`): dense и sparse по id кандидатов одним
пакетом `query_batch_points` (обращение к Qdrant по-прежнему одно), у РАВНЫХ score — равный ранг (лучший
из занятых мест), RRF по формуле Qdrant. Формула сверена: Qdrant 1.18 складывает 1/(2 + ранг), ранг с нуля —
пересчёт по двум спискам совпал с `FusionQuery` до 7e-8 (точность float32); без ничьих окно то же.

**Замер.** `scripts/eval_okpd2_climb.py` (EXACT_SEARCH, коллекции `pp719_ed1031`), по два прогона подряд
на трёх кодах. Сбоев, проглоченных пересчётом или доборами, в журналах прогонов — 0 (один прогон упал на
исчерпании портов Windows при шести параллельных процессах — перезапущен, в замер не входит).

Шумовой пол — смены целевой между двумя прогонами одного кода (own 1569 / climb 1281 / control 600):

| Код | own | climb | control | первая в окне сменилась | порядок окна сменился |
|---|---|---|---|---|---|
| `v0.5.0-test42` (без `R31`) | 3 | 0 | 0 | 0 / 0 / 0 | 10 / 1 / 2 |
| `dev` `9e8e9a7` (`R31`) | 8 | **4** | **4** | 0 / 4 / 4 | 37 / 43 / 13 |
| `dev` + `R31-2` | 3 | **0** | **0** | 0 / 0 / 0 | 16 / 19 / 3 |

* `dev`: climb — ровно «Краски» 20.30.24 и три подкода (XXI/27 ↔ XXI/30); control — XIV (20.13.21.220,
  20.11.99, 20.14.99.000, 20.11.13.110: «Катализаторы …» меняются местами).
* own 3 с правкой — те же, что у test42 (28.25.13.110, позиции XVIII под 26.51.11.190 / 28.99.39.190 и т. п.):
  порядок НЕСКОЛЬКИХ целевых, первая та же. Это ничьи основного пула (top-40 до пересчёта), они были до `R31`.
* Остаток «порядок окна» с правкой — хвост окна (первое расхождение на месте 1–3 и ниже), целевые не
  меняются. Источник тот же — пул: его состав на границе top-40 зависит от ничьих `FusionQuery`, а ранги
  пересчёта зависят от состава. Лечится тем же слиянием на нашей стороне в общем `_hybrid` — это все ветки
  (товарная, процедурная, кейсы), отдельная правка со своим замером, в `test43` не входит — **#247** `R31-3`.

Радиус против `dev` (`--compare`, оба прогона): **починено 0, сломано 0** во всех трёх популяциях; целевая
сменилась без смены вердикта у 21–23 own, 9 climb, 21–23 control. Проверено поимённо, что это ничьи: **53 из 54**
смен — на вопросах, где в списках пересчёта есть равные score; единственная без ничьей (own 28.25.13.110)
плавает и на `dev`, и на test42 — шум пула, а не правка.

**Релизная проверка `test43`** — новый пункт: «Краски полиграфические 20.30.24», восемь прогонов `search`
подряд — один порядок top-3 (без правки совпадают с вероятностью ~1 %). С правкой — 29 проверок, 0 провалов;
`dev` без правки — 1 провал, ровно этот пункт (2 порядка за 8 прогонов); код test42 — 26 из 28.

**Решение по `test43`:** `R31` едет вместе с `R31-2`. Откат `R31` не нужен: целевые устойчивы, как на test42.
