> Прошлый прогон — [2026-08-17_EV1-EV4.md](2026-08-17_EV1-EV4.md); методика — [EVAL_GUIDE](../../EVAL_GUIDE.md).

## 1. Гейт мерил сам себя

`scripts/eval_determinism.py` строил эталон «чужих чисел» так:

```python
own    = claim_numbers(format_context([target], query))
others = claim_numbers(format_context([target, h], query))   # для каждого кандидата
return others - own
```

`EV7` убрал требования нецелевых кандидатов **из `format_context`**. Значит после правки
`others == own` **по построению**, и разность пуста при любом поведении модели.

Проверено прогоном на фикстуре тех самых насосов, ради которых заводилась `EV7` (кандидат несёт
110, 450 и порог 750):

```
foreign_numbers → ПУСТО
```

Гейт не мог опуститься ниже 1.00 на ветке без кода — а это **8 из 10** запросов набора. Отчёт
«гейт ≥0.95 пройден впервые» опирался на число, которое не могло быть другим.

**Как чинилось.** Эталон строится из ЗАПИСИ, а не из рендера: порог позиции, пороги узлов (`D9`),
баллы операций, величины внутри текстов требований и условий блоков. Такой оракул переживает любую
правку рендера, в том числе обратную.

**Плюс канал, которого метрика не видела вовсе.** `_plan_answer` кладёт `format_cases` и в промпт,
и в строку заземления, правило 1а даёт кейсу эксперта ВЫСШИЙ приоритет, а часть кейсов несёт баллы
и проценты. После `EV7` это единственный оставшийся канал чужих чисел — теперь он в метрике.

**Защита от повторения.** В отчёт добавлена величина «сколько чужих чисел было ДОСТУПНО к утечке».
Без неё «1.00» не интерпретируется: пустой пул даёт единицу при любом поведении. На боевом наборе
пул — **209 чисел на 9 запросах из 10**, то есть гейт снова что-то проверяет.

## 2. Частичный код обходил правку целиком

`okpd2_match` иерархический, и рантайм помечал совпавшими ВСЕ записи ветки. Замер по корпусу:

| Код | Записей под префиксом | Операций | Контекст ДО | Контекст ПОСЛЕ |
|---|---|---|---|---|
| `28.13` | 52 | 531 | 15 799 симв., 11 уник. чисел, 8 целевых | **6 194 симв., 0 чисел, 1 целевая** |
| `29.10` | 23 | 1 001 | 16 928 симв., 5 чисел, 8 целевых | **5 389 симв., 2 числа, 1 целевая** |
| `28.15.10` | 1 в окне | — | 5 026 симв., 9 чисел | 5 026 симв., 9 чисел (не затронут) |

То есть пользователь, назвавший код — самый желанный сценарий продукта, — защиты не получал вовсе,
а контекст выходил БОЛЬШЕ, чем до `EV7`. Теперь код-ГРУППА даёт одну целевую позицию, а ТОЧНОЕ
совпадение — все записи этого кода (у 26.11.22.210 их две, требования поделены между ними).

Живая проверка ответа на код-группу: сервис честно говорит «поиск вернул несколько позиций, но
целевая одна», называет её и печатает требования; незаземлённых чисел ноль.

## 4. Цена `EV7` была обоснована неверно

В коде и в трёх документах стояло: «единственная просьба сравнить позиции из 580 вопросов волны
пришла С КОДОМ, значит обе записи совпадают по коду и обе остаются целевыми». Проверено дословно:

```
«можешь сравнить требования по нашему коду 28.13.14 и по 26.30.50»
extract_okpd2 → 28.13.14        # только первый
```

`extract_okpd2` — это `re.search`, одно совпадение. Вторая позиция целевой не становится, и `EV7`
убирает её требования. То есть ровно тот вопрос, которым обосновывалась безопасность правки, ею и
ломается. Утверждение убрано из кода и документов, задача заведена — **#88**.

## 5. Метрика разошлась с продуктом прямо во время перезамера

Первый перезамер faithfulness дал **0.95** — два кейса «выдумали» числа (#11 оптические волокна
`27.31.12.110`, шесть чисел; #21 ноутбуки `26.20.11`). Рантайм-гард не пометил **ни одного**: 0 из 2.
Расходились не ответ и данные, а две функции об одном и том же — контекст стал зависеть от кода, а
`eval_answers` пересобирал его вызовом `format_context(ans.hits, query)` БЕЗ кода.

Починено в корне: `Answer.grounding` несёт ровно ту строку, с которой сверялся гард, и все три
скрипта берут её оттуда. После этого faithfulness — **1.00 (422 числа, 0 выдуманных)**.

⚠ В самом `eval_answers` уже стояло предупреждение ЭТОГО ЖЕ класса — про забытый `question`. Оно
не помешало наступить в капкан второй раз через другой параметр: комментарий не защищает, защищает
инвариант.

## 5а. «Отказ вне сферы 3/4» — артефакт детектора, а не регресс

В одном прогоне из трёх кейс #28 («оказываем юридические и бухгалтерские консультации») отчитался
как «без отказа». Точечная проверка (шесть прогонов подряд) показала: **ответ отказывает корректно
каждый раз** — «это услуги, а не промышленная продукция, поэтому вне сферы действия ПП №719», —
а мимо бьёт `DECLINE_RE`, который ищет отказ по СПИСКУ СЛОВ («вне сфер|не относ|уточнит|…»).
Изредка модель формулирует отказ, не употребив ни одного из них.

Это ровно урок 36 в другой одежде: **признак «какой это ответ» надо брать из ФОРМЫ, предписанной
промптом, а не из фразы, которая может появиться или не появиться.** Правка не сделана сознательно:
менять детектор нужно вместе с перезамером, а перезамер только что закончен. Заведено как долг.

⚠ Попутно замечено: top-1 на этом запросе — запись, чьё наименование начинается с
«до 1 января 2019 г.: наличие у юридического лица - налог…», то есть **фрагмент требования, ставший
именем позиции**. Класс дефекта данных, родственный `D4`; проверить объём отдельной задачей.

## 6. Что осталось долгом

* **Детерминизм набора чисел 0.90 ± 0.08** при пороге 0.95. Плавают «городские автобусы» и
  «гусеничные бульдозеры» — мега-продукты, где модель выбирает подмножество из десятков операций.
  Это остаток `K6` (бюджет на стороне ЦЕЛЕВОГО хита), а не утечка: гейт чужих чисел на них чист.
* **#88** — сравнение по нескольким кодам.
* **#89** — роль строки расколотой ячейки должна лежать в данных, а не в регулярке по прозе:
  под неё подходят 16 записей корпуса, из них **13 — настоящая продукция**.
* Формулировка «в контексте баллы не указаны» в живом ответе выносит внутреннюю лексику
  пользователю и читается как пробел в данных — класс `R7`, жалоба №1 платного теста.
* `DECLINE_RE` ловит отказ по словам, а не по форме (см. §5а).
* Запись с наименованием-фрагментом требования («до 1 января 2019 г.: наличие у юридического
  лица…») — проверить, сколько таких в корпусе.

## 7. Уроки

Занесены в память проекта (пп. 37–38) и ниже — коротко:

1. **Оракул метрики нельзя выводить из артефакта, который она проверяет.** Тот же класс, что
   «эталон нельзя размечать регулярками» (`K12`). Маскируется тем, что число двигается в
   успокаивающую сторону и совпадает с ожиданием от правки.
2. **Рядом с метрикой печатать размер пула.** «0 нарушений» интерпретируется только вместе с
   «из скольких возможных».
3. **Правка, проверенная на одной ветке маршрута, на другой может не действовать вовсе.** Гейт
   набирался из запросов без кода — ветка с кодом просто не измерялась.
4. **Предупреждение в комментарии не защищает от капкана, который оно описывает.** Защищает то,
   что делает ошибку невозможной: артефакт несёт своё заземление.
