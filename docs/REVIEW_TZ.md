### `[ ]` R6 — наследование требований по группам (T11) · **P0** · 2–3 сессии

**Проблема — корневая для приёмки.** **349 позиций (26 % базы) не имеют ни одной операции
требований.** На каждый четвёртый вопрос система физически не может показать требования — либо
молчит, либо подтягивает требования соседней позиции.

Концентрация: **XVIII судостроение — 101**, **XXI нефтегазохимия — 84**, VII медизделия — 35,
XI — 19, III — 16, I — 16. Примеры (раздел II): `29.10.51`, `29.10.59.310`, `29.10.59.280`,
`29.10.59.390` — дочерние строки групп с `requirement_blocks: []`, требования которых лежат в
родительской строке.

**Что сделать (поэтапно, с проверкой на каждом шаге).**
1. **Диагностика.** Скрипт `scripts/diag_orphan_requirements.py`: для каждой из 349 позиций найти
   в исходном чанке родительскую строку-группу; классифицировать: (а) требования наследуются от
   родителя, (б) позиция исключена/справочная, (в) дефект нарезки.
2. **Начать с XVIII и XXI** — 185 из 349 позиций, половина проблемы в двух разделах.
3. **Реализация — parent/child на уровне payload, без смены схемы коллекции:** добавить в запись
   поля `parent_anchor` и `inherited_blocks`; `format_context` показывает унаследованные требования
   с явной пометкой «требования группы «<родитель>»» — **дословно, с указанием источника**.
4. Отдельно пометить позиции категории (б) — чтобы ответ говорил «позиция справочная/исключена»,
   а не «требования не найдены».

**Риск (осознать до старта).** Неверное наследование = неверные баллы, а это хуже, чем «требований
не найдено». Поэтому: наследование показывать **только** с явной атрибуцией к родителю и **никогда**
не суммировать баллы автоматически. Матрица «категория × компонент» (авто, суда) — не в этой задаче.

**Критерий приёмки.** Число позиций без требований снижено с 349 до ≤120 (закрыты XVIII, XXI, VII);
